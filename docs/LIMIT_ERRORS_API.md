# عقد أخطاء حدود الباقات

هذا العقد يكمل [سياسة الحساب والاستهلاك](LIMITS_POLICY_AR.md). تنفذ المصانع المشتركة في `app/services/limit_errors.py`، وتستخدمها خدمات الاستحقاقات والاستخدام والحصص وطبقة كثافة الطلبات.

## بنية الاستجابة

```json
{
  "detail": {
    "code": "PLAN_LIMIT_EXCEEDED",
    "limit_key": "events_per_month",
    "current": 1,
    "limit": 1,
    "requested": 1,
    "message": "تم تجاوز الحد الأقصى لـ 'الفعاليات شهرياً'. الحالي: 1، المسموح به: 1، المطلوب: 1."
  }
}
```

`code` و`message` موجودان في جميع الأخطاء المدرجة. القيم العددية والحقول الأخرى تعتمد على نوع الخطأ؛ لا يفترض العميل وجود `current` في خطأ ميزة أو كثافة طلبات. النص عربي وقابل للتغيير؛ `code` هو أساس تصنيف الخطأ. لا تصنف رسالة 429 تلقائياً على أنها تتطلب ترقية.

| الرمز | HTTP | الحقول الإضافية | المعالجة المناسبة |
|---|---|---|---|
| `PLAN_LIMIT_EXCEEDED` | 429 | `limit_key`, `current`, `limit`, `requested`، وللشهرية `resets_at`, `timezone` | عرض استخدام المورد؛ مراجعة الباقة أو تحرير سعة مورد ثابت حسب السياسة |
| `EVENT_QUOTA_EXCEEDED` | 400 | `event_id`, `ticket_class`, `limit_key`, `current`, `limit`, `requested` | مراجعة حصة فئة الدعوات داخل الفعالية؛ ليست بالضرورة مشكلة في الباقة |
| `FEATURE_NOT_INCLUDED` | 403 | `feature_key` | مراجعة الباقات والصلاحية لإدارة الاشتراك |
| `FEATURE_DISABLED` | 403 | `feature_key` | مراجعة مسؤول الحساب؛ الترقية لا تلغي تعطيل الميزة صراحةً |
| `PLAN_LIMIT_NOT_CONFIGURED` | 402 | `limit_key` | مراجعة الدعم وإعداد المورد؛ لا يعني بلوغ حد الاستخدام |
| `RATE_LIMIT_EXCEEDED` | 429 | `limit`, `retry_after` بالثواني | الانتظار ثم إعادة المحاولة؛ ليس خطأ اشتراك |
| `USAGE_BUSY` | 409 | `limit_key`, `retry_after` | عملية أخرى لنفس الحساب تحجز رصيد الاستهلاك حالياً (مثل توليد كبير). انتظر ثوانٍ وأعد المحاولة؛ ليست مشكلة اشتراك. يرافقها `Retry-After` |

رفض ضبط مجموع حصص VIP والعادية على قيمة أكبر من سقف الدعوات الشهري يتضمن `operation: "event_capacity_configuration"`. في هذه الحالة `current=0` و`requested` هما حساب القيمة المراد ضبطها؛ لا يمثلان قراءة عداد الشهر ولا يتم استهلاك دعوات بهذه العملية.

خطأ كثافة الطلبات العام يحافظ على `Retry-After` و`X-RateLimit-Limit`. حدود مسارات المصادقة العامة المستقلة تعيد `Retry-After` طبقاً لنافذة الحماية الخاصة بها؛ الرقم فترة انتظار محافظة، وليس قياساً دقيقاً للوقت المتبقي في النافذة المنزلقة.

## حدود النطاق

أخطاء الصلاحيات والمصادقة والتحقق من المدخلات والأعطال التشغيلية تظل مستقلة. أخطاء غياب الباقة الصالحة أو بيانات الباقة المخصصة غير الصحيحة ليست مصنفة كتجاوز استخدام. التنبيه المشترك `LimitErrorNotice` يستخدم هذا العقد لعرض إجراء الباقات أو إدارة حصة الفعالية أو الانتظار. رصيد الشهر وموعد تجديده يصدران من الخادم بتوقيت UTC.

## توافق العملاء والإطلاق

رموز HTTP السابقة محفوظة، لكن تغيير `detail` من نص إلى كائن هو تغيير في جسم الاستجابة، وليس توافقاً كاملاً مع عميل قديم يفترض نصاً. لذلك:

1. العملاء المحدثون يقبلون `detail` النصي القديم والكائن الجديد مع `message`.
2. الواجهة الرئيسية تستخدم `getApiErrorMessage()` لعرض النص، و`getApiErrorCode()` للتمييز المنظم. تبقى بيانات الحد الأصلية في الاستجابة دون تحويل أو حذف.
3. عميل PWA وعميل Expo يستخرجان الرسالة من النص أو `detail.message`.
4. عند النشر، حدث العملاء أولاً ثم الخادم، وتحقق من تحديث عملاء الأجهزة والنسخ المخزنة قبل الاعتماد على الجسم الجديد. العملاء الخارجيون يحتاجون نفس التحديث.
5. تظل رسائل التسجيل المنظمة التي تحتوي `message` و`fields` و`issues` قابلة للعرض بالمعالج المشترك.
