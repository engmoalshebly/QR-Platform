# دليل ربط أرقام WhatsApp والإرسال عبر API

**الإصدار:** 1.0 — **التاريخ:** 20 أكتوبر 2026.

هذا الدليل يشرح الآلية المتاحة فعلياً في النشر الحالي: إضافة رقم مرسل من لوحة OpenWA، أو تنفيذ خطوات الربط بواسطة API، ثم إرسال رسالة من الجلسة المرتبطة بذلك الرقم. الأمثلة لا تتضمن مفاتيح حقيقية ولا تنفذ أي إرسال بمجرد فتح المستند.

## 1. العناوين والمفاهيم

| الاستخدام | العنوان |
|---|---|
| لوحة إدارة OpenWA | https://notify.prideidea.com/dashboard |
| أصل API الخاص بـOpenWA | https://notify.prideidea.com/api |
| API خدمة الإشعارات ذات الطابور | https://notify.prideidea.com/v1 |
| التوثيق التفاعلي لخدمة الإشعارات | https://notify.prideidea.com/docs |

**رقم المرسل** هو الرقم الذي سيرتبط بهاتف WhatsApp عبر QR. **الجلسة** سجل مستقل لذلك الاتصال، وله `id` بصيغة UUID. **رقم المستلم** هو الشخص الذي تريد مراسلته، ولا يحتاج جلسة. الإرسال المباشر يختار رقم المرسل بواسطة `session_id` في المسار، وليس عبر حقل `from`.

| الخاصية | OpenWA المباشر `/api` | خدمة الإشعارات `/v1` |
|---|---|---|
| المصادقة المستخدمة في هذا الدليل | `X-API-Key` | `Authorization: Bearer` |
| إنشاء جلسة وربط رقم وعرض QR | متاح | غير متاح |
| اختيار جلسة محددة لكل إرسال | عبر معرّف الجلسة في المسار | غير متاح حالياً؛ جلسة واحدة في إعداد الخادم |
| طابور دائم ومنع التكرار | لا يقدم عقد الطابور وIdempotency الخاص بخدمتنا | متاح |
| متابعة النتيجة | معرّف المزود وسجل الرسائل وWebhooks | معرّف الإشعار وحالاته عبر GET |

مفاتيح OpenWA ومفاتيح خدمة الإشعارات منفصلة ولا تتبادل الوظائف. لوحة OpenWA ليست لوحة إدارة عملاء خدمة الإشعارات.

## 2. المتطلبات والصلاحيات

- هاتف الرقم المرسل عليه WhatsApp، وصاحب الرقم متاح لمسح QR.
- صلاحية دخول اللوحة أو مفتاح OpenWA مناسب على خادم النظام الذي ينفذ التكامل.
- اتصال HTTPS من النظام المصدر إلى العنوان المنشور.
- للأمثلة الطرفية: `curl` و`jq`، ومتغيرات بيئة محملة من مخزن أسرار.

| المفتاح / الدور | الاستخدام |
|---|---|
| OpenWA `admin` | إدارة المفاتيح والجلسات، وإصدار مفاتيح مقيدة |
| OpenWA `operator` | إنشاء/تشغيل الجلسات والإرسال وفق القيود الممنوحة |
| OpenWA `viewer` | قراءة؛ لا يكفي للإرسال أو تشغيل الجلسة |
| مفتاح نظام الإشعارات `ntf_...` | إرسال ومتابعة إشعارات ذلك النظام عبر `/v1` فقط |

مفتاح الدخول الإداري للوحة محفوظ على الخادم في `/home/alrazi/.qentry/openwa-dashboard-admin.json` بصلاحية `600`. لا تسلمه للأنظمة العميلة. استخدم قيمة `api_key` فقط للدخول إلى اللوحة.

**حدود العزل:** تقييد مفتاح OpenWA بـ`allowedSessions` يحمي المسارات التي تحتوي معرّف جلسة. بعض مسارات القائمة العامة لا تحتوي معرّف جلسة ولا تطبق عزلاً كاملاً لكل عميل. لذلك لا تعامل مفاتيح OpenWA كبديل لعزل المؤسسات في منتج متعدد العملاء؛ احتفظ بها في خادم مركزي موثوق، وقدّم للأنظمة الخارجية واجهة محدودة تناسب حاجتها.

## 3. المسار الأول: إضافة الرقم من الواجهة ثم الإرسال عبر API

### 3.1 إضافة وربط الرقم

1. افتح **https://notify.prideidea.com/dashboard**.
2. أدخل مفتاح إدارة OpenWA في **API Key** ثم اضغط **Connect**.
3. افتح **Sessions** ثم **New Session**.
4. أدخل اسماً فريداً مثل `orders-sender` واضغط **Create**. استخدم حروفاً إنجليزية صغيرة وأرقاماً وشرطات؛ الطول من 3 إلى 50 حرفاً.
5. اضغط **Start** في بطاقة الجلسة الجديدة. اعرض QR إذا لم يفتح تلقائياً.
6. من الهاتف: **WhatsApp ← الأجهزة المرتبطة ← ربط جهاز**، ثم امسح QR.
7. انتظر **Connected**؛ وهي تقابل `status=ready` في API.
8. افتح تفاصيل الجلسة وانسخ `id`. تحقق من رقم `phone` المعروض قبل اعتمادها للإرسال.

ربط جلسة جديدة لا يغير جلسة المنصة أو مرسل خدمة الإشعارات تلقائياً. لا توقف أو تحذف الرقم القائم بغرض إضافة رقم آخر.

### 3.2 إصدار مفتاح تكامل مقيد بهذه الجلسة

أنشئ المفتاح عبر API من خادم الإدارة. نافذة **API Keys** الحالية تنشئ مفاتيح بالدور المختار، لكنها لا توفر حقلاً لتحديد `allowedSessions`؛ استخدم الطلب أدناه للحصول على القيد صراحة.

المتغيرات المطلوبة:

```dotenv
OPENWA_API_BASE=https://notify.prideidea.com/api
OPENWA_ADMIN_KEY=<مفتاح إدارة OpenWA>
OPENWA_SESSION_ID=<معرف الجلسة المرتبطة بالرقم الجديد>
```

```bash
# تعيد apiKey مرة واحدة؛ احفظ الاستجابة في ملف محمي، ولا تسجلها في logs.
umask 077
curl --fail-with-body --silent --show-error \
  "$OPENWA_API_BASE/auth/api-keys" \
  -H "X-API-Key: $OPENWA_ADMIN_KEY" \
  -H 'Content-Type: application/json' \
  --data "$(jq -n --arg sid "$OPENWA_SESSION_ID" \
    '{name:"orders-sender-integration",role:"operator",allowedSessions:[$sid]}')" \
  > openwa-integration-key.json
```

احفظ `apiKey` في مخزن أسرار النظام باسم `OPENWA_SEND_KEY`، واحفظ `id` كمعرّف المفتاح لإلغائه لاحقاً. لا تضع ملف المفاتيح في Git. يمكن إضافة `expiresAt` كتاريخ ISO 8601 مستقبلي لفرض انتهاء صلاحية المفتاح.

### 3.3 التحقق من الجلسة

```bash
curl --fail-with-body --silent --show-error \
  "$OPENWA_API_BASE/sessions/$OPENWA_SESSION_ID" \
  -H "X-API-Key: $OPENWA_SEND_KEY"
```

مثال استجابة مختصر، والبيانات تمثيلية:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "name": "orders-sender",
  "status": "ready",
  "phone": "9677XXXXXXXX"
}
```

لا ترسل قبل `ready` والتحقق من `phone`. قيمة الاسم ليست رقم الهاتف ولا يثبت إنشاؤها ملكية رقم.

### 3.4 إرسال رسالة من الرقم المرتبط

اضبط `RECIPIENT_NUMBER` لرقم مستلم مصرح بمراسلته، بالأرقام الدولية فقط دون `+` أو مسافات، مثل رمز البلد ثم الرقم. `OPENWA_SEND_KEY` هو مفتاح الجلسة، وليس مفتاح الإدارة.

```bash
curl --fail-with-body --silent --show-error \
  "$OPENWA_API_BASE/sessions/$OPENWA_SESSION_ID/messages/send-text" \
  -H "X-API-Key: $OPENWA_SEND_KEY" \
  -H 'Content-Type: application/json' \
  --data "$(jq -n --arg phone "$RECIPIENT_NUMBER" \
    --arg text 'تم تأكيد طلبك بنجاح.' \
    '{chatId:($phone+"@c.us"),text:$text}')"
```

استجابة نجاح تمثيلية:

```json
{"messageId":"provider-message-id","timestamp":1792470000}
```

`messageId` يعني أن المزود أعاد نتيجة إرسال. لا يثبت التسليم أو القراءة. احفظه مع معرّف العملية التجارية ومعرّف الجلسة.

**سلوك إعادة المحاولة:** هذا المسار لا يوفر `Idempotency-Key` الخاص بخدمة الإشعارات. إذا انتهت المهلة أو انقطع الاتصال أثناء POST، فقد تكون الرسالة خرجت. لا تعد إرسال الطلب تلقائياً؛ سجل النتيجة كغير محسومة وراجع سجل الجلسة أو هاتف المرسل. يلزم طابور ومنع تكرار في نظامك عند استخدام النقل المباشر.

## 4. المسار الثاني: ربط الرقم بالكامل عبر API

يمكن للنظام المركزي تنفيذ خطوات الجلسة وعرض QR في واجهته، لكن يبقى مسح QR من الهاتف خطوة لازمة لإثبات الربط. إدخال رقم هاتف في طلب API وحده لا ينشئ اتصال WhatsApp مصادقاً عليه. لا توجد في الآلية الموثقة هنا مصادقة عبر SMS أو رمز OTP أو pairing code.

### 4.1 إنشاء الجلسة

ينفذ خادم الإدارة الطلب؛ لا تكشف مفتاح الإدارة لواجهة المتصفح:

```bash
curl --fail-with-body --silent --show-error \
  "$OPENWA_API_BASE/sessions" \
  -H "X-API-Key: $OPENWA_ADMIN_KEY" \
  -H 'Content-Type: application/json' \
  --data '{"name":"customer-42-sender","config":{"autoReconnect":true}}'
```

استجابة مختصرة:

```json
{
  "id":"11111111-1111-4111-8111-111111111111",
  "name":"customer-42-sender",
  "status":"created",
  "phone":null
}
```

احفظ `id` باسم `OPENWA_SESSION_ID`. في قاعدة نظامك اربطه بالجهة المالكة للرقم. اسم الجلسة فريد؛ احفظ المعرف بمجرد نجاح الإنشاء. إذا ضاع رد الإنشاء، استعلم إدارياً عن الجلسات وابحث بالاسم نفسه قبل إنشاء سجل آخر.

أصدر بعدها مفتاح operator مقيداً بهذه الجلسة كما في **3.2**. تستعمله بقية طلبات التشغيل والـQR والإرسال. يحتفظ خادم الإدارة بالمفتاح الإداري منفصلاً.

### 4.2 بدء جلسة الربط

```bash
curl --fail-with-body --silent --show-error -X POST \
  "$OPENWA_API_BASE/sessions/$OPENWA_SESSION_ID/start" \
  -H "X-API-Key: $OPENWA_SEND_KEY"
```

نجاح الطلب لا يعني أن الهاتف مرتبط. قد تبدأ الحالة بـ`initializing` قبل تجهيز QR. لا تكرر `start` كل عدة ثوانٍ؛ إذا كانت الجلسة قد بدأت فقد يعيد `400`، واستعلم عن الحالة بدلاً من افتراض الفشل أو إنشاء جلسة بديلة.

### 4.3 جلب QR وعرضه

```bash
curl --fail-with-body --silent --show-error \
  "$OPENWA_API_BASE/sessions/$OPENWA_SESSION_ID/qr" \
  -H "X-API-Key: $OPENWA_SEND_KEY"
```

استجابة:

```json
{"qrCode":"data:image/png;base64,...","status":"qr_ready"}
```

قيمة `qrCode` هي Data URL جاهزة لوضعها في `src` لصورة. لا تضف لها بادئة base64 أخرى. تعامل معها كبيانات ربط حساسة، ولا تخزنها في سجلات أو ملفات عامة.

في واجهة نظامك:

```html
<img id="whatsapp-qr" alt="امسح الرمز من واتساب لربط الرقم" />
```

```javascript
// الربط بمسار من خادم نظامك؛ هذا المسار المقترح تنفذه أنت وليس endpoint منشوراً لدينا.
// خادمك يتحقق من ملكية المستخدم للجلسة ويضيف مفتاح OpenWA المحفوظ لديه.
const response = await fetch('/internal/whatsapp/connection/qr', { cache: 'no-store' });
if (response.ok) {
  const data = await response.json();
  document.getElementById('whatsapp-qr').src = data.qrCode;
}
```

اطلب حالة الجلسة دورياً أثناء الربط، مثلاً كل خمس ثوانٍ. عندما تكون `qr_ready` اجلب QR الحالي بدلاً من عرض صورة قديمة. `400` من مسار QR قد يعني أنه لم يجهز، أو انتهت صلاحيته، أو أن الربط اكتمل بالفعل؛ افحص حالة الجلسة لتحدد التصرف. ضع مهلة لعملية الربط في واجهتك وأوقف polling عند المغادرة أو اكتمالها.

### 4.4 مسح الرمز وتأكيد الرقم

يعرض النظام QR لصاحب الرقم ليقوم بمسحه من WhatsApp على الهاتف. ثم يستعلم الخادم:

```bash
curl --fail-with-body --silent --show-error \
  "$OPENWA_API_BASE/sessions/$OPENWA_SESSION_ID" \
  -H "X-API-Key: $OPENWA_SEND_KEY"
```

عند `status=ready` تحقق من أن `phone` يطابق الرقم المتوقع في نظامك. لا تعتبر الحساب مربوطاً بالرقم المقصود لمجرد مسح QR؛ قد يمسحه هاتف آخر مخول بفتح الشاشة. عند عدم المطابقة أوقف اعتماد الاتصال وراجع المسؤول.

### 4.5 الإرسال

استخدم الطلب نفسه في **3.4**. الفرق بين المسارين هو كيفية إنشاء وربط الجلسة؛ عقد الإرسال واحد بعد الوصول إلى `ready`.

## 5. مثال Python للإرسال من جلسة محددة

```python
import os
import httpx

base = os.environ['OPENWA_API_BASE'].rstrip('/')
session_id = os.environ['OPENWA_SESSION_ID']
headers = {'X-API-Key': os.environ['OPENWA_SEND_KEY']}
recipient = os.environ['RECIPIENT_NUMBER']

with httpx.Client(timeout=30, follow_redirects=False) as client:
    state = client.get(f'{base}/sessions/{session_id}', headers=headers)
    state.raise_for_status()
    if state.json()['status'] != 'ready':
        raise RuntimeError('WhatsApp session is not ready')

    try:
        response = client.post(
            f'{base}/sessions/{session_id}/messages/send-text',
            headers=headers,
            json={'chatId': recipient + '@c.us', 'text': 'تم تأكيد طلبك بنجاح.'},
        )
    except httpx.TransportError as exc:
        # سجل العملية كغير محسومة؛ لا تنفذ إعادة إرسال عمياء.
        raise RuntimeError('Send result unknown; review before retry') from exc
    response.raise_for_status()
    message_id = response.json()['messageId']
    # احفظ message_id مع العملية التجارية ومعرف الجلسة.
```

مثال النقل المباشر ليس طابوراً كاملاً. قد يكون لبعض أخطاء الخادم أو رد غير قابل للقراءة أثر خارجي حدث فعلاً؛ طبق السياسة نفسها للنتيجة غير المحسومة بدلاً من افتراض أن الرسالة لم تخرج.

## 6. التسليم والقراءة عبر Webhook

إذا كان نظامك يستخدم OpenWA المباشر ويحتاج تأكيد الوصول، سجل Webhook مستقلاً للجلسة. لا تعدل اشتراكات منصة الدعوات أو خدمة الإشعارات القائمة.

```bash
curl --fail-with-body --silent --show-error \
  "$OPENWA_API_BASE/sessions/$OPENWA_SESSION_ID/webhooks" \
  -H "X-API-Key: $OPENWA_SEND_KEY" \
  -H 'Content-Type: application/json' \
  --data "$(jq -n --arg url "$CALLBACK_URL" --arg secret "$CALLBACK_SECRET" \
    '{url:$url,events:["message.ack"],secret:$secret,retryCount:5}')"
```

اضبط `CALLBACK_URL` على HTTPS في خادمك، و`CALLBACK_SECRET` على سر عشوائي مستقل. احفظ معرّف الاشتراك المعاد، ولا تكرر إنشاء الاشتراك لكل رسالة. الاشتراك مرتبط بالجلسة؛ احتفظ بربط رسائل نظامك بمعرّفات المزود لتجاهل إيصالات الرسائل التي لا تخص نظامك.

المزود يرسل `X-OpenWA-Signature` بقيمة `sha256=<hex>`. تحقق من HMAC-SHA256 على **بايتات جسم الطلب الأصلية قبل تحليل JSON** باستخدام السر، ثم تحقق من `sessionId` و`event` والحقول المطلوبة. لا تثق في جسم غير موقع. العقد المهم للإيصال:

```json
{
  "event":"message.ack",
  "sessionId":"11111111-1111-4111-8111-111111111111",
  "data":{"messageId":"provider-message-id","ack":2}
}
```

هذا مثال مختصر، وقد توجد حقول إضافية مثل timestamp ومعرّفات الحدث والتسليم.

| ack | المعنى العملي |
|---|---|
| -1 | خطأ/رفض للرسالة |
| 0 | قيد الانتظار |
| 1 | إقرار خادم WhatsApp؛ لا يثبت التسليم للمستلم |
| 2 | تسليم إلى المستلم |
| 3 | قراءة |
| 4 | تشغيل/استهلاك الوسائط؛ لا تحتاجه الرسائل النصية عادة |

احفظ الإيصال بشكل دائم قبل الرد 2xx، وتعامل مع التكرار باستخدام الجلسة ومعرف الرسالة وقيمة ack، واحفظ الإيصال المبكر إذا سبق استجابة الإرسال. لا تخفض `read` إلى `delivered` إذا وصل إشعار قديم متأخراً. غياب إيصال قراءة لا يثبت أن المستلم لم يقرأ الرسالة.

## 7. استخدام الرقم الجديد مع خدمة الإشعارات ذات الطابور

إذا كنت تريد `POST /v1/notifications` والطابور ومنع التكرار، فاختيار مرسل لكل طلب **غير متاح في الإصدار الحالي**. لديك الخياران التاليان:

1. استعمال OpenWA المباشر للجلسة الجديدة، مع إدارة نظامك للطابور والتكرار ونتائج النقل غير المحسومة.
2. تخصيص الجلسة الجديدة كمرسل لخدمة الإشعارات الحالية، فيصبح هو المرسل لجميع أنظمتها.

لتنفيذ الخيار الثاني بواسطة مسؤول الخادم:

- راجع الطلبات المنتظرة وأوقف الخدمة قبل تغيير المرسل؛ تغيير الجلسة يؤثر على الرسائل المعلقة أيضاً.
- حدّث `/home/alrazi/.qentry/notifications.env` بقيم `OPENWA_SESSION_ID` و`OPENWA_API_KEY` الخاصة بالجلسة الجديدة، دون تغيير مفاتيح عملاء `/v1`.
- احتفظ بنسخة إعدادات محمية وخطة رجوع. عند تبديل المرسل، راجع اشتراك Webhook السابق ومعالجة الإيصالات المتأخرة؛ لا تحذف اشتراكاً يخص تطبيقاً آخر.
- أعد إنشاء الخدمة وسجل اشتراكها ثم افحصها:

```bash
# الإيقاف أولاً، قبل تحرير ملف البيئة
 docker compose -f notification-service/compose.yml stop notification-api
# حرر ملف البيئة المحمي هنا بالقيم الجديدة، ثم:
 docker compose -f notification-service/compose.yml up -d --force-recreate notification-api
python3 notification-service/register_webhook.py
python3 notification-service/manage.py connection
```

لا تغير `OPENWA_WEBHOOK_SECRET` مع نقل الجلسة دون مراعاة الاشتراكات والرسائل السابقة. لا ترسل من الجلسة الجديدة حتى يؤكد الفحص رقمها وحالتها. للاحتفاظ بعدة أرقام وإتاحة اختيار مرسل لكل نظام أو لكل إشعار مع طابور مركزي، يلزم تطوير سجل مرسلين وربط صلاحيات المفاتيح بهم؛ هذه الإمكانية ليست جزءاً منفذاً من API الحالي.

دليل خدمة الإشعارات وأمثلة `Idempotency-Key`: [README_AR.md](../notification-service/README_AR.md).

## 8. الحالات والأخطاء وإدارة الاتصال

| حالة الجلسة | الإجراء |
|---|---|
| created | ابدأ الجلسة |
| initializing | انتظر تجهيز المحرك |
| qr_ready | اعرض QR الحالي لصاحب الرقم |
| authenticating | انتظر نتيجة المصادقة |
| ready | تحقق من phone ثم اسمح بالإرسال |
| disconnected | أوقف الإرسال وراجع الهاتف والاتصال؛ قد تحتاج start أو QR جديداً |
| failed | راجع السبب وحالة الخدمة قبل إعادة التشغيل |

| HTTP | التعامل |
|---|---|
| 2xx | نجاح الطلب المعني، وليس بالضرورة اكتمال الربط أو التسليم |
| 400 | اقرأ رسالة الخطأ؛ مثل جلسة بدأت بالفعل، أو QR غير جاهز، أو جلسة غير متصلة |
| 401 / 403 | تحقق من المفتاح والدور والانتهاء وقيد الجلسة؛ قد يعاد 401 لقصور الصلاحية |
| 404 | تحقق من UUID والمسار والاشتراك المطلوب |
| 409 | قد يكون اسم الجلسة مستخدماً؛ استعد سجلها بدلاً من إنشاء بديل بلا تحقق |
| 429 | أبطئ الطلبات؛ لا تعالج ضغط الإرسال بتكرار متوازٍ |
| 5xx / timeout أثناء إرسال رسالة | نتيجة قد تكون غير محسومة؛ راجع قبل إعادة الإرسال |

إيقاف جلسة دون حذف سجلها:

```bash
curl --fail-with-body -X POST \
  "$OPENWA_API_BASE/sessions/$OPENWA_SESSION_ID/stop" \
  -H "X-API-Key: $OPENWA_SEND_KEY"
```

حذف الجلسة إجراء صريح لإزالة اتصال لا تحتاجه؛ ليس خطوة عادية لإعادة المحاولة. إلغاء مفتاح تكامل من خادم الإدارة:

```bash
curl --fail-with-body -X POST \
  "$OPENWA_API_BASE/auth/api-keys/$OPENWA_KEY_ID/revoke" \
  -H "X-API-Key: $OPENWA_ADMIN_KEY"
```

## 9. قائمة قبول التكامل

- الجلسة تخص الجهة الصحيحة، وحالتها `ready` ورقمها مطابق للمتوقع.
- النظام يستخدم مفتاح operator مقيداً بالجلسة؛ مفتاح الإدارة باقٍ في خادم الإدارة.
- بيانات QR والمفاتيح لا تظهر في logs أو روابط أو كود متصفح عام.
- اختبرت رسالة واحدة مقصودة، وحفظت معرّفها، وفصلت الإرسال عن التسليم.
- حددت سياسة واضحة للـtimeout والتكرار والإيصالات المتأخرة قبل تشغيل رسائل العملاء.
- حددت هل تستخدم النقل المباشر أم خدمة الطابور، ولم تفترض أن إضافة رقم في UI تغيّر مرسل `/v1` تلقائياً.

## 10. مراجع التنفيذ وحدود التحقق

العقود راجعت على: `OpenWA/src/modules/session/session.controller.ts` وDTO الجلسة، و`message.controller.ts` وDTO الرسائل، ووحدة مفاتيح API وWebhooks. النشر السابق تحقق عملياً من الدخول وإنشاء جلسة مؤقتة وعرض QR واشتراك WebSocket ثم حذف الجلسة دون ربط هاتف أو إرسال. إعداد هذا المستند لم ينشئ جلسات أو مفاتيح ولم يرسل رسائل إضافية. أمثلة الاستجابات مختصرة وتمثيلية؛ لا تنسخ UUID أو معرّف الرسالة التمثيلي كقيم تشغيل.

دليل اللوحة والنشر: [OPENWA_DASHBOARD_AR.md](OPENWA_DASHBOARD_AR.md).


## 11. مجموعة Postman المرافقة

استورد [OPENWA_NUMBER_ONBOARDING_POSTMAN.json](OPENWA_NUMBER_ONBOARDING_POSTMAN.json). تحتوي طلبات الإنشاء وإصدار المفتاح والبدء وQR والحالة والإرسال وWebhooks والإيقاف والإلغاء. القيم السرية وأرقام التشغيل فارغة عمداً. بعد الإنشاء انسخ `id` إلى `session_id`، وبعد إصدار المفتاح انسخ `apiKey` إلى `session_key` و`id` إلى `key_id`. احفظ المفاتيح في Postman Vault أو متغيرات محلية محمية، ولا تشارك تصدير بيئة يحتويها. لا تشغل المجموعة كاملة دفعة واحدة؛ طلب الإرسال يراسل رقماً فعلياً، وطلبا الإيقاف والإلغاء يغيران حالة الاتصال أو المفتاح.
