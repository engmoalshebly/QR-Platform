# خطة إصلاح إنشاء الدعوات وتجهيزه للإنتاج والأعداد الكبيرة

التاريخ: 13 أكتوبر 2026 — بتوقيت عدن.
آخر تحديث: 18 أكتوبر 2026 — بتوقيت برلين.

هذه خطة تنفيذ مبنية على [المراجعة الفعلية](INVITATION_GENERATION_REVIEW_AR.md) و[أدلة الاختبارات](INVITATION_GENERATION_REVIEW.json). الحالة الحالية: **P0 منشورة؛ P1 مكتملة بالتحقق المحلي؛ P2 مكتملة بالتحقق المحلي؛ P3 مكتملة بالتحقق المحلي**. لا تعني كتابة الخطة تحقق السعة أو جاهزية الإنتاج.

النتيجة المستهدفة: عملية إنشاء واحدة يمكن متابعتها واستكمالها، تتسع لعشرة آلاف سجل، وتعمل ضمن موارد محددة، ولا تكرر الدعوات أو تدعي نجاحاً ناقصاً. تحتفظ المنصة بآلاف العمليات وتدير انتظارها، بينما تنفذ عدداً محدوداً منها بالتوازي بحسب السعة المثبتة.

## ترتيب التنفيذ وحالة المراحل

تنفذ المراحل بالترتيب التالي. كل مربع غير مؤشّر يعني أن المهمة لم تنفذ؛ لا تُغلق مرحلة دون إرفاق دليل الاختبارات ومخرجاتها.

| المرحلة | النتيجة الأساسية | يعتمد على | الحالة |
|---|---|---|---|
| [المرحلة 1: P0](#phase-p0) | إصلاح صحة المسارات الحالية | — | مكتملة |
| [المرحلة 2: P1](#phase-p1) | حفظ العمليات ومنع التكرار | P0 | مكتملة |
| [المرحلة 3: P2](#phase-p2) | العامل والاستعادة والإلغاء | P1 | مكتملة محليًا |
| [المرحلة 4: P3](#phase-p3) | الاستيراد الكبير والملفات المحدودة | P2 | مكتملة محليًا |
| [المرحلة 5: P4](#phase-p4) | الواجهة الموحدة ومتابعة العمليات | P3 | قيد التنفيذ |
| [المرحلة 6: P5](#phase-p5) | إثبات السعة والتشغيل | P4 | لم تبدأ |
| [المرحلة 7: P6](#phase-p6) | النشر التدريجي واعتماد الإنتاج | P5 | لم تبدأ |

المرحلة المنجزة: **المرحلة 1 — P0** ([نتائج الإصلاح والتحقق](INVITATION_GENERATION_P0_RESULTS_AR.md)). أنجزت **المرحلة 2 — P1** أيضًا ([نتائجها](INVITATION_GENERATION_P1_RESULTS_AR.md)). أُنجزت **المرحلة 3 — P2** محليًا أيضًا ([التنفيذ والتحقق](INVITATION_GENERATION_P2_PROGRESS_AR.md)). نُفذت **المرحلة 4 — P3** محليًا وأعيد التحقق منها ضمن دفعة الجاهزية ([نتائجها](INVITATION_GENERATION_P3_RESULTS_AR.md)). **المرحلة 5 — P4** قيد التنفيذ ([التقدم](INVITATION_GENERATION_P4_PROGRESS_AR.md)). تجهيز تصاميم الواجهة والاختبارات ممكن مبكراً، بينما اعتمادها مرتبط بمراحل الخادم السابقة. حدود 10,000 سجل وألف عملية منتظرة تبقى أهدافاً حتى تثبتها المرحلة 6 وتعتمدها المرحلة 7.

## طريقة متابعة التنفيذ

لكل مرحلة سجل إنجاز يذكر المهام المنفذة، والملفات والترحيلات المتغيرة، ونتائج الاختبارات، والعوائق، ودليل اكتمالها. تستخدم رموز المهام مثل P0-01 للربط بالتغييرات والاختبارات. الحالات المعتمدة: لم تبدأ، قيد التنفيذ، جاهزة للتحقق، مكتملة. لا تستعمل «مكتملة» لمرحلة بقيت بوابة قبولها غير محققة.

<a id="phase-p0"></a>

## المرحلة 1 — P0: إصلاح صحة المسارات الحالية

**الحالة:** مكتملة ومنشورة؛ [دليل النشر](INVITATION_GENERATION_P0_DEPLOYMENT.json).

**يعتمد على:** لا توجد مرحلة سابقة؛ هذه نقطة البداية.

**الهدف:** تصحيح العيوب المثبتة قبل إضافة قدرة جديدة أو تغيير دورة الإنشاء.

### المهام

- [x] **P0-01** — توحيد الاسم والفئة وعدد الأشخاص والهاتف والبريد بين العدد والأسماء وExcel والتصميم، ورفض المدخلات المخالفة بوضوح.
- [x] **P0-02** — نقل الاتصال إلى الحقول الأصلية، ودعم guest.phone وguest_phone و«رقم الجوال»، وفصل RSVP عن الحقول المطبوعة.
- [x] **P0-03** — فصل عدد البطاقات عن عدد الأشخاص، وتوحيد حساب الحصة واستثناء الحالات الملغاة، وعرض «غير محدود» عندما تكون الحصة صفراً.
- [x] **P0-04** — منع نجاح التوليد السريع بعد سقوط رمز، ومنع ready عند نقص PDF أو ZIP أو بطاقات، مع حساب الفشل من الحالة الفعلية.
- [x] **P0-05** — إصلاح عرض العربية في PDF السريع واختبار الأسماء العربية والإنجليزية والمختلطة وVIP.
- [x] **P0-06** — تطبيق صلاحيات التصدير والميزة عند إنشاء الملفات وإرجاعها وتنزيلها؛ توحيد حراسة الأزرار.
- [x] **P0-07** — تجديد روابط التنزيل، وإظهار حدود الألف الحالية قبل الإرسال إلى أن يعتمد مسار الاستيراد الكبير.
- [x] **P0-08** — تحويل فحوص العيوب في تقرير المراجعة إلى اختبارات تتوقع السلوك الصحيح، وتوثيق نتيجة كل إصلاح.

### المخرجات

إصلاحات محدودة للمسارات الحالية، واختبارات رجوع، وتقرير يربط كل عيب بتغييره ونتيجة التحقق.

### شروط الاكتمال

تنجح اختبارات العيوب والاختبارات القائمة؛ تتطابق العدادات والاتصال؛ لا نجاح ناقص أو ملف غير مصرح؛ تُطبع العربية بصورة صحيحة.

**التفاصيل المرتبطة:** [عقد البيانات والتحقق](#reference-4)، [الصلاحيات والروابط](#reference-8).

<a id="phase-p1"></a>

## المرحلة 2 — P1: حفظ العمليات ومنع التكرار

**الحالة:** مكتملة بالتحقق المحلي؛ [نتائج المرحلة](INVITATION_GENERATION_P1_RESULTS_AR.md). لم تُنشر P1 أو تُفعّل بعد؛ اكتمال العامل في P2 شرط تشغيل العقد الجديد.

**يعتمد على:** اكتمال P0 وتثبيت عقد البيانات والصلاحيات.

**الهدف:** إنشاء عملية رئيسية محفوظة، وقبول ذري لا يكرر الدعوات أو يخصم الحصة مرتين.

### المهام

- [x] **P1-01** — إضافة نموذج العمليات والاستيراد والملفات وoutbox، وربط generation_batches وbatch_items بالعملية الرئيسية.
- [x] **P1-02** — إضافة قيود التفرد للطلب والسجل والدفعة، والفهارس وعلاقات المؤسسة وRLS، بترحيلات إضافية متوافقة.
- [x] **P1-03** — توثيق واجهات قبول العملية وقراءة حالتها ونتائجها، مع عقد جديد يرجع 202 دون تغيير الرد القديم بصمت.
- [x] **P1-04** — قبول الطلب والدعوات والحصة والدفعات وoutbox في معاملة واحدة قصيرة، باستخدام إدخال مجموعي.
- [x] **P1-05** — إعادة العملية نفسها عند تكرار المفتاح والبصمة، ورفض إعادة استخدام المفتاح لمدخلات مختلفة بـ409.
- [x] **P1-06** — حفظ نسخة ثابتة للإعدادات وعناصر القالب والخطوط وأصول الخلفية، ومنع تغيير نتيجة العملية بتعديل القالب لاحقاً.
- [x] **P1-07** — تطبيق سقف الطابور والمؤسسة قبل قبول العملية أو خصم الاستخدام، مع سبب واضح وRetry-After.
- [x] **P1-08** — اختبار التزامن على الطلب نفسه وآخر مقاعد الحصة، وعزل مؤسسات مختلفة وصلاحيات الإنشاء دون التصدير.

### المخرجات

ترحيلات وعقد API موثق وخدمة عمليات موحدة وقبول ذري وهوية ثابتة للعملية.

### شروط الاكتمال

مئة طلب متزامن بالمفتاح نفسه تنشئ عملية واحدة ودعوات واستخداماً واحداً؛ فقد الاستجابة لا يكرر الإنشاء؛ تجتاز RLS والحصص الاختبارات.

**التفاصيل المرتبطة:** [القرارات الأساسية](#reference-2)، [البنية المقترحة وحفظ العمليات](#reference-5)، [الصلاحيات والروابط](#reference-8).

<a id="phase-p2"></a>

## المرحلة 3 — P2: العامل والاستعادة والإلغاء

**الحالة:** مكتملة بالتحقق المحلي — رُبط الناشر بالعامل والتوليد المجمد، ونُفذت الاستعادة والإلغاء وإعادة المراحل الفاشلة. التشغيل الجديد معطّل افتراضيًا ولم يُنشر إلى الإنتاج. انظر [التنفيذ والتشخيص](INVITATION_GENERATION_P2_PROGRESS_AR.md) و[دليل الاختبارات والصورة](INVITATION_GENERATION_P2_RESULTS.json).

**يعتمد على:** اكتمال P1 ووجود عمليات وoutbox محفوظين.

**الهدف:** معالجة قابلة للاستكمال تتحمل فقد العامل أو Redis وتعيد المرحلة الفاشلة فقط.

### المهام

- [x] **P2-01** — نقل التوليد السريع والمصمم إلى العامل، وإزالة fallback الإنتاجي الذي ينفذ التوليد داخل API.
- [x] **P2-02** — تنفيذ ناشر outbox ونقل معرّفات العمل فقط إلى Redis، مع تحمل تكرار نشر المهمة.
- [x] **P2-03** — فصل مراحل الرمز والتصميم والتصدير، وتنفيذ ملكية العامل وlease وheartbeat ورقم تنفيذ يمنع تثبيت نتيجة عامل قديم.
- [x] **P2-04** — إضافة فاحص استعادة للدفعات بلا عامل والملكية المنتهية، وتصنيف الأخطاء والمحاولات المؤقتة المحدودة.
- [x] **P2-05** — تنفيذ queued/running/completed/partial/failed/cancel_requested/cancelled، مع انتقالات شرطية وتقدم للبطاقات والملفات كلٌ على حدة.
- [x] **P2-06** — تنفيذ الإلغاء التعاوني بين الوحدات والمراحل، ومنع نشر نتيجة بعد تثبيت الإلغاء.
- [x] **P2-07** — إعادة الفاشل من العملية نفسها دون إنشاء دعوات أو احتساب استخدام جديد، وإعادة بناء العدادات دون تضخيم.
- [x] **P2-08** — اختبار موت العامل وتكرار المهمة وعودة عامل قديم وفشل الرفع وPDF/ZIP وانقطاع Redis أثناء المعالجة.

### المخرجات

عامل بمراحل مستقلة، وناشر outbox، وفاحص استعادة، وإلغاء وإعادة آمنين، ودليل تشخيص أولي.

### شروط الاكتمال

لا فقد أو تكرار لعملية مقبولة في اختبارات الانقطاع؛ لا عاملان يثبتان نتيجة متضاربة؛ يتوقف الملغى فعلياً وتُعاد المرحلة المطلوبة وحدها.

**التفاصيل المرتبطة:** [البنية المقترحة وحفظ العمليات](#reference-5)، [الحالات والإلغاء وإعادة المحاولة](#reference-7).

<a id="phase-p3"></a>

## المرحلة 4 — P3: الاستيراد الكبير والملفات المحدودة

**الحالة:** مكتملة بالتحقق المحلي؛ أعيد التحقق في 20 أكتوبر ضمن مجموعة 948 اختبارًا ناجحًا، دون اعتماد للسعة الإنتاجية. لم يُنشر أو يُفعّل في الإنتاج. [سجل التنفيذ والقياسات](INVITATION_GENERATION_P3_PROGRESS_AR.md).

**يعتمد على:** اكتمال P1 وP2؛ رفع حد الإنتاج يحتاج إثبات P5 واعتماد P6.

**الهدف:** معالجة 10,000 سجل دون تحميل بيانات العملية وصورها كلها في ذاكرة الخادم أو المتصفح.

### المهام

- [x] **P3-01** — رفع XLSX/CSV والتحقق من نوعه وحدوده وفك ضغطه، وقراءته تدريجياً مع اختيار ورقة البيانات.
- [x] **P3-02** — حفظ الصفوف المطَبَّعة والأخطاء وخريطة الأعمدة والاختيار على الخادم؛ توفير بحث وتصفية وصفحات وتصدير للمخالفات.
- [x] **P3-03** — توضيح المقبول والمرفوض والمستبعد والفئات، واشتراط اختيار ظاهر قبل توليد جزء من الملف.
- [x] **P3-04** — تقسيم السريع إلى دفعات أولية نحو 250 بطاقة، وتقسيم التصميم بوحدات صفحات تحافظ على ترتيب وخانات QR.
- [x] **P3-05** — إضافة مساحة عمل خاصة على القرص خارج tmpfs، مع سقف للمساحة وتنظيف آمن للملفات المهجورة.
- [x] **P3-06** — توليد PDF/ZIP تدريجياً وتقسيمهما بحسب الحجم والصفحات، مع manifest وربط كل جزء بالدعوات التي يغطيها.
- [x] **P3-07** — التحقق من حجم وبصمة واكتمال الملف قبل النشر؛ تحرير الذاكرة بعد كل وحدة وعدم استبدال ملف منشور عشوائياً.
- [x] **P3-08** — اختبار 1,000 و10,000 سجل، والأرقام العربية، والملفات المختلطة والمخالفة، والذاكرة والمساحة ومحتوى الأرشيف.

### المخرجات

استيراد مرحلي ومعاينة وأخطاء بصفحات، ودفعات محدودة، وملفات بأجزاء متحققة، وتنظيف مساحة العمل.

### شروط الاكتمال

تتطابق 10,000 بطاقة مع الصفوف المختارة والمخرجات؛ لا سقوط صفوف أو OOM؛ تبقى الذاكرة والحجم ضمن الحدود المعتمدة في القياس.

**التفاصيل المرتبطة:** [حدود السعة ومعنى «آلاف العمليات»](#reference-1)، [التقسيم والذاكرة والملفات](#reference-6)، [الاستيراد والواجهة عند الأعداد الكبيرة](#reference-9).

## المرحلة 5 — P4: الواجهة الموحدة ومتابعة العمليات

**الحالة:** قيد التنفيذ؛ [التقدم والمتبقي](INVITATION_GENERATION_P4_PROGRESS_AR.md). أُنجز P4-04 وP4-05 وP4-07 بالتحقق المحلي، والبقية لم تُنجز.

**يعتمد على:** عقد P1 ثابت؛ اعتماد المرحلة بعد اكتمال P2 وP3. يمكن تجهيز التصميم مبكراً.

**الهدف:** واجهة واضحة للأعداد الكبيرة، تستعيد المسودة والمتابعة وتوضح النجاح الكامل والجزئي والفشل.

### المهام

- [ ] **P4-01** — ترتيب الإنشاء إلى اختيار المخرجات، وإدخال البيانات، والمراجعة، ثم الإنشاء والمتابعة.
- [ ] **P4-02** — عرض البطاقات والأشخاص والفئات والحصة والأخطاء والاختيار بوضوح قبل التأكيد.
- [ ] **P4-03** — إظهار RSVP وخيارات التصدير في الحالات والصلاحيات المناسبة فقط، مع شرح مختصر وراء زر صغير.
- [x] **P4-04** — إضافة سجل عمليات مصفح ومفلتر، واستعادة العملية بعد تحديث الصفحة أو تسجيل الدخول أو العودة إلى الحدث.
- [x] **P4-05** — إظهار تقدم البطاقات والملفات منفصلين، وأجزاء التنزيل وسبب الفشل وما سيعاد، دون وصف 202 بأنه نجاح مكتمل.
- [ ] **P4-06** — ترحيل المسودات الكبيرة إلى الخادم بعد حفظ ناجح وصلاحية صحيحة؛ إبقاء تفضيلات العرض غير الحساسة محلياً.
- [x] **P4-07** — ترحيل كل مستهلك للإنشاء، ومنها EventBarcodesTab، إلى العقد الجديد مع احترام الفترة الانتقالية.
- [ ] **P4-08** — اختبار الكمبيوتر والجوال وlight/dark وتحديث الصفحة وتبديل الحساب/المؤسسة، وضبط polling عند الخطأ والحالات النهائية.

### المخرجات

واجهة إنشاء موحدة، وسجل عمليات ومتابعة قابلة للاستعادة، وتنزيل وإعادة واضحة، واختبارات متصفح.

### شروط الاكتمال

تنجح اختبارات كل طرق الإدخال؛ لا فقد متابعة أو تسرب مسودة؛ لا جدول ضخم؛ الحالة والعدادات والصلاحيات تطابق الخادم.

**التفاصيل المرتبطة:** [رحلة المستخدم المقترحة](#reference-3)، [الصلاحيات والروابط](#reference-8)، [الاستيراد والواجهة عند الأعداد الكبيرة](#reference-9).

## المرحلة 6 — P5: إثبات السعة والتشغيل

**الحالة:** لم تبدأ.

**يعتمد على:** اكتمال P0 إلى P4 وتشغيل نسخة مماثلة للإنتاج في staging.

**الهدف:** إثبات حدود السعة والأداء والاستعادة وتوفير مراقبة وتشغيل قابلين للاعتماد.

### المهام

- [ ] **P5-01** — تسجيل موارد المعالج والذاكرة والقرص والتخزين واتصالات PostgreSQL، وضبط التزامن وعدالة المؤسسات وفقها.
- [ ] **P5-02** — اختبار 1 و100 و1,000 و10,000 سجل، وسريع ومصمم، والتحقق من أعداد الملفات وفك QR وطباعة العربية.
- [ ] **P5-03** — اختبار ألف عملية صغيرة منتظرة عبر مؤسسات متعددة ضمن سقف البطاقات، وحمل قراءة 100 مستخدم متزامن.
- [ ] **P5-04** — تشغيل اختبار ثماني ساعات مع زيادة تدريجية للحمل وتسجيل p95 و429 و5xx والانتظار والذاكرة والمساحة.
- [ ] **P5-05** — اختبار إعادة تشغيل API والعامل وRedis، وانقطاع النقل عشر دقائق، والإلغاء وإعادة المحاولة تحت الحمل.
- [ ] **P5-06** — تجهيز المؤشرات والتنبيهات ولوحة التشغيل، دون أسماء أو هواتف أو signed tokens في logs أو labels.
- [ ] **P5-07** — تجهيز نسخة خارجية مشفرة، واختبار استعادة البيانات والملفات، وكتابة دليل الاستعادة والتشخيص والإيقاف.
- [ ] **P5-08** — إصدار تقرير سعة يحدد الحدود التي نجحت فعلياً والموارد المستخدمة؛ تعديل الموارد ثم إعادة الاختبار عند عدم بلوغ الأهداف.

### المخرجات

تقرير تحميل وتشغيل طويل واستعادة، وإعدادات موارد مثبتة، ومراقبة وتنبيهات ودليل تشغيل ونسخ احتياطية متحققة.

### شروط الاكتمال

تتحقق أهداف الأداء والاستعادة؛ peak ذاكرة العامل دون 70% من حده المعتمد؛ لا فقد أو تكرار أو نجاح ناقص؛ تُعتمد السعة من التقرير.

## المرجع التفصيلي للمراحل

التفاصيل التالية جزء من الخطة وتستخدم أثناء التنفيذ والتحقق. ترتيب التنفيذ المعتمد هو المراحل السبع أعلاه.

<a id="reference-1"></a>

### مرجع 1 — حدود السعة ومعنى «آلاف العمليات»

| البند | الهدف الأولي | شرط اعتماده |
|---|---|---|
| سجلات الدعوات في العملية الواحدة | حتى 10,000 | اختبار يشمل البيانات والرفع والمخرجات والاستعادة |
| الأشخاص في البطاقة الواحدة | عدد صحيح من 1 إلى الحد المعتمد، 100 مبدئياً | اتساق التحقق والحصة والبوابة وRSVP |
| العمليات المنتظرة | حتى 1,000، مع سقف مستقل لمجموع البطاقات المنتظرة | اختبار الطابور والقراءة والاستعادة؛ ليست ألف مهمة CPU متزامنة |
| مجموع البطاقات المنتظرة | 100,000 مبدئياً | قياس قاعدة البيانات والتخزين ووقت تفريغ الطابور؛ قيمة قابلة للضبط |
| العمليات الجارية/المنتظرة للمؤسسة | 10 مبدئياً | سياسة عادلة قابلة للتعديل حسب الخطة |
| التنفيذ المتزامن | يبدأ بعامل توليد واحد ومهمة ثقيلة واحدة | يُزاد تدريجياً بعد قياس الذاكرة والمعالج والتخزين |
| عرض الجداول والمعاينات | 50 صفاً، خيارات 25 و100 | بحث وتصفية وترقيم على الخادم |
| أجزاء الملفات | حد حجم مبدئي 25MiB للجزء | قياس الحجم الفعلي، لا تقدير العدد وحده |

هذه حدود تصميم أولية وليست سعة مثبتة للخادم الحالي. إذا امتلأ الطابور يرفض الخادم قبول عملية جديدة برسالة واضحة وRetry-After، قبل إنشاء الدعوات أو خصم الاستخدام. يسمح السجل التاريخي بآلاف العمليات، ويعرضها بصفحات مستقلة عن حجم الطابور النشط.

السجل الحالي أثبت أن توليد 1,000 رمز وPDF/ZIP محلياً استغرق نحو 52 ثانية ووصل peak RSS إلى نحو 432MiB، دون قاعدة البيانات أو الرفع أو التصميم. ملف Compose يحدد للعامل 768M ومعالجاً واحداً وتزامناً مقداره 2؛ لا نعتمد هذا التزامن للمهام الثقيلة قبل القياس. لا يُستخدم القياس المحلي كموعد إنجاز مضمون للعملاء.

<a id="reference-2"></a>

### مرجع 2 — القرارات الأساسية

1. تتجه طرق العدد والأسماء وExcel، السريعة والمصممة، إلى عقد بيانات ومحرك عمليات موحدين.
2. لا ينفذ طلب إنشاء العملية رسم الصور أو بناء الملفات؛ يقبل عملية محفوظة ويرجع معرّفها، وتبدأ المعالجة في العامل.
3. PostgreSQL هو مصدر حقيقة العملية وحالاتها. Redis ينقل المهام ولا يكون السجل الوحيد الذي تعتمد عليه الاستعادة.
4. لا تعني إعادة تسليم مهمة للعامل إنشاء دعوات جديدة. نستخدم قيود تفرد وهوية ثابتة للطلب والعناصر والمخرجات.
5. بيانات الاتصال مستقلة عن الحقول المرئية للقالب، وتصميم العملية وأصولها محفوظة بنسخة ثابتة.
6. لا توجد نتيجة «جاهزة بالكامل» دون التحقق من البطاقات وكل الملفات المطلوبة. الفشل الجزئي نتيجة صريحة.
7. إنشاء الدعوات لا يرسل WhatsApp أو بريداً تلقائياً. الإرسال يبقى إجراءً منفصلاً بصلاحياته وطابوره الحاليين.

<a id="reference-3"></a>

### مرجع 3 — رحلة المستخدم المقترحة

تظل واجهة الإنشاء مختصرة، بأربع خطوات واضحة:

1. **نوع المخرجات:** رموز للطباعة أو كروت مصممة؛ اختيار الفئات والقوالب المطلوبة.
2. **بيانات الضيوف:** عدد تلقائي، أسماء يدوية، أو ملف Excel/CSV. تعرض البطاقات والأشخاص والفئات كلٌ على حدة.
3. **مراجعة قبل الإنشاء:** معاينة بصفحات، أخطاء الصفوف، بيانات الاتصال، عدد الصفوف المختارة والمستبعدة، الحصة، وخيارات RSVP والطباعة المتاحة.
4. **إنشاء ومتابعة:** يظهر رقم العملية وحالتها وتقدم البطاقات والملفات. يمكن مغادرة الصفحة والعودة، وتنزيل الأجزاء الجاهزة، وإعادة الفاشل من العملية نفسها.

يعرض الملف المختلط عدد العادي وVIP بوضوح. في التصميم، يختار المستخدم قالباً لكل فئة، أو يختار توليد فئة واحدة مع بيان الصفوف المستبعدة قبل التأكيد. لا يستبعد النظام فئة أو صفاً مخالفاً دون قرار ظاهر للمستخدم.

RSVP يظهر عند إتاحة الميزة ووجود بيانات ضيوف مناسبة؛ لا يظهر في التوليد المجهول بالعدد. الهاتف والبريد يُدخلان كبيانات اتصال حتى لو لم يظهرا في الكرت. الشرح التفصيلي يبقى وراء زر صغير «طريقة الاستخدام».

<a id="reference-4"></a>

### مرجع 4 — عقد البيانات والتحقق

يعتمد كل مسار حقولاً موحدة: الاسم، الفئة، عدد الأشخاص، الهاتف، WhatsApp، البريد، حقول العرض، ورقم الصف الأصلي. لا تُرسل حقول العرض مفرودة فوق الحقول الأساسية بما يسمح باستبدالها.

- طبّع الأرقام العربية والفارسية، والمسافات، وأسماء الأعمدة العربية والإنجليزية إلى حقول معروفة.
- ارفض العدد السالب والكسور والقيم غير الرقمية. لا تحوّل قيمة مخالفة إلى 1 بصمت.
- ارفض الاسم الفارغ والفئة غير المعروفة والقيم التي تتجاوز أطوالها المسموحة. الحقول المفقودة الاختيارية فقط لها defaults موثقة.
- اقبل الهاتف بصيغة دولية، أو استعمل رمز دولة اختاره المستخدم بوضوح. لا تخمّن الدولة من رقم محلي.
- افحص صيغة البريد؛ هذا ليس ضماناً لقابلية التسليم. التحقق من تسجيل رقم WhatsApp يحدث في مسار الإرسال، لا عبر آلاف الاستدعاءات أثناء الاستيراد.
- اقبل guest.phone وguest_phone و«رقم الجوال» كبدائل للمعنى نفسه، واحفظ القيمة في حقول الاتصال الأصلية.
- احفظ بيانات العرض في custom_fields، دون جعلها المصدر الوحيد للاتصال.
- يبقى الضيف المكرر في الملف قراراً بشرياً: نعرض تحذيراً وتطابق الهاتف/البريد/الاسم، ولا نحذف سجلات قد تكون مقصودة تلقائياً.
- يعمل تحقق الواجهة والخادم بالقواعد نفسها، مع الخادم كجهة اعتماد نهائية.

تُفصل العدادات: `cards_count` عدد سجلات الدعوات، و`people_count` مجموع الأشخاص، ثم توزيع الفئات وعدد الصفوف المقبولة والمرفوضة والمختارة. تُحسب صفحات الطباعة من البطاقات وخانات القالب، وتُحسب حصص الحدث من الأشخاص. quota=0 تعني «غير محدود» كما في الخادم الحالي.

<a id="reference-5"></a>

### مرجع 5 — البنية المقترحة وحفظ العمليات

يُضاف نموذج عملية رئيسية، مع الاستفادة من generation_batches وbatch_items الحالية كدفعات فرعية. لا نحذف السجل القديم أو نغير معنى ready فيه إلى نجاح جزئي.

| البيانات | الغرض والضمان المطلوب |
|---|---|
| `generation_operations` | المؤسسة والحدث والمنشئ ومعرّف الطلب وبصمة المدخلات والعدادات والحالة ونسخة الإعدادات والقالب |
| `generation_imports` و`generation_import_rows` | ملف المصدر، الصف الأصلي، القيم المطَبَّعة، الأخطاء، الاختيار ونسخة التحقق؛ قراءة بصفحات |
| إضافات إلى `generation_batches` | operation_id وترتيب الجزء ومرحلة العمل والمحاولة وملكية التنفيذ ومهلة العامل |
| إضافات إلى `batch_items` | ربط السجل الأصلي؛ فصل حالة الرمز عن التصميم بدل تحميل render_status جميع المعاني |
| `generation_outbox` | أحداث تشغيل محفوظة في المعاملة نفسها، مع وقت الإرسال والمحاولات والإعادة |
| `generation_artifacts` | مسار تخزين خاص ونوع الملف وحجمه وبصمته وترتيبه ونسخة manifest وحالة التحقق |
| ربط الملف بالعناصر | تحديد الدعوات التي يغطيها كل جزء بدقة، بما فيها الصفوف غير المتجاورة وإعادة الفاشل |

قيود أساسية: طلب واحد لكل `(tenant_id, idempotency_key)`، ودعوة واحدة لكل `(operation_id, source_row_id)`، ودفعة واحدة لكل ترتيب ومرحلة معتمدين. يجب أن تمنع علاقات المؤسسة ربط عنصر أو قالب أو ملف بعملية من مؤسسة أخرى.

كل جدول جديد له RLS وفهارس للمؤسسة والحدث والحالة والترتيب ووقت الإنشاء. تستخدم الطلبات دور التطبيق غير المتجاوز لـRLS. العامل يتعامل فقط مع مؤسسة العملية المثبتة، ويضع tenant_id في القراءة والتحديث حتى عند استخدام جلسة البنية التحتية المميزة.

تُراجع أرقام الترحيلات المتاحة عند التنفيذ؛ لا نعتمد أرقاماً محجوزة افتراضياً أو نغير ترحيلات منشورة.

#### قبول العملية والحصة في معاملة واحدة

1. يتحقق الخادم من الطلب الثابت ونسخة البيانات والقالب والصلاحيات والميزات والسعة المتاحة.
2. إذا وجد الطلب نفسه وبصمته نفسها، يعيد العملية الموجودة. البصمة المختلفة بالمفتاح نفسه ترجع 409.
3. يفحص حصة الأشخاص وحدود الخطة ويستخدم قفل الحصة الحالي لمدة المعاملة فقط.
4. ينشئ العملية والدعوات مرة واحدة من الصفوف المختارة المتحققة، باستخدام إدخال مجموعي من البيانات المرحلية أو توليد العدد. لا ينفذ آلاف استدعاءات INSERT منفردة.
5. ينشئ الدفعات الفرعية وأحداث outbox ويثبت الاستخدام ضمن المعاملة نفسها؛ أي فشل يعيدها كلها.
6. يعيد 202 ومعرّف العملية. لا ينتظر رسم الصور أو رفع الملفات.

هذا القرار يحجز الحصة بواسطة الدعوات المنشأة فعلياً؛ لا نضيف حجزاً ثانياً يحسب الأشخاص مرتين. إعادة ملفات العملية لا تخصم حصة إنشاء جديدة. فشل توليد الملف لا يمحو دعوة ربما أصبحت مستخدمة؛ إلغاء الدعوات نفسها إجراء منفصل ومدقق وفق سياسة الإلغاء الحالية.

إذا تجاوز إدخال 10,000 دعوة زمن القبول المستهدف، يعالج ذلك بإدخال مجموعي وفهارس وموارد مناسبة. لا يُستبدل بمعاملات إنشاء مجزأة دون تصميم حجز حصة مستقل واختباره لمنع تجاوز الحصص.

#### نقل المهام واستعادتها

يقرأ ناشر outbox الأحداث القابلة للإرسال بقفل قصير، وينشر معرّف العمل فقط. فشل Redis يبقي الحدث قابلاً للإعادة. تكرار النشر ممكن ومتعمد؛ منع تكرار الأثر يحدث في قاعدة البيانات، وليس بمجرد task_id في Celery.

عند استلام المهمة، يطالب العامل بالدفعة بتحديث شرطي يحصل منه على lease ورقم تنفيذ متزايد. لا يطالب بها عاملان معاً. يرسل heartbeat، وتجدد الملكية خلال المهام الطويلة. كل تحديث ونشر نتيجة يشترط ملكية التنفيذ الحالية؛ العامل القديم لا يستطيع تثبيت نتيجة بعد انتهاء ملكيته.

قيم البداية القابلة للضبط: heartbeat كل 15 ثانية، lease لمدة دقيقتين، وفاحص استعادة كل 30 ثانية. تصنّف الأخطاء إلى قابلة للإعادة، ومخالفة بيانات، ومخالفة صلاحية، ونتيجة تحتاج تحققاً. الأخطاء المؤقتة لها انتظار متزايد وعدد محاولات محدود؛ لا يعاد خطأ البيانات بلا إصلاح.

يفحص المجدول انتظار outbox والدفعات بلا عامل والملكية المنتهية. يفحص العناصر والملفات المثبتة قبل إعادة العمل، ولا يعيد العملية من الصفر. يعيد بناء العدادات من الحالات المحفوظة عند الحاجة دون تضخيمها بفعل تكرار المهمة.

<a id="reference-6"></a>

### مرجع 6 — التقسيم والذاكرة والملفات

- يبدأ السريع بدفعات نحو 250 بطاقة، وتُضبط بالقياس. التصميم يبدأ بوحدات صفحات صغيرة مع احترام عدد خانات QR في الصفحة؛ لا تقطع دفعةً بطريقة تكرر الضيف أو تكسر توزيع الخانات.
- يعالج العامل صورة/صفحة أو مجموعة محدودة، يرفعها ويثبت نتيجتها ثم يحرر الذاكرة. لا يحتفظ بصور العملية كاملة حتى نهاية 10,000 سجل.
- تُكتب PDF وZIP على مساحة عمل خاصة قائمة على القرص، خارج `/tmp` الحالي المركب كـtmpfs؛ استخدام tempfile فوق tmpfs لا يحل ضغط الذاكرة.
- تُحدد سعة مساحة العمل، ويمنع قبول عمل جديد عند انخفاض المساحة. تنظيف الملفات المهجورة يراعي ملكية عامل نشط ولا يحذف عملاً ما زال جارياً.
- تقسم المخرجات بحجمها وعدد صفحاتها مع manifest ثابت يوضح الجزء وعدد بطاقاته وحجمه. ZIP من أجزاء مستقل عن PDF من أجزاء.
- تجميع ملف واحد كبير يكون خياراً لاحقاً له سقف مثبت، ولا يتطلب تحميل جميع أجزائه في ذاكرة المتصفح.
- يعاد فقط الرمز/الصفحة/الجزء الفاشل. ملف PDF فاشل لا يستدعي إنشاء الضيوف أو رسم كل الصور من جديد.
- تحفظ الملفات في مسارات إصدار غير قابلة للاستبدال بالـupsert العشوائي. نشر manifest يتم فقط بعد التحقق من الملفات وربطها بالعناصر؛ الملفات المرفوعة وغير المنشورة تُنظف بعد مهلة آمنة.
- تحفظ نسخة عناصر القالب وأبعاد اللوحة والخطوط والتحويلات وأصول الخلفية في مسارات ثابتة أو بإصدارات وبصمات. تعديل القالب أثناء الانتظار لا يغير مخرجات العملية المقبولة.

يحسن حجم QR وصور الطباعة بعد اختبار فك الرموز والعربية والوضوح؛ لا تُخفّض الجودة أو دقة المسح للحصول على أرقام أداء أفضل.

<a id="reference-7"></a>

### مرجع 7 — الحالات والإلغاء وإعادة المحاولة

| الحالة | معناها وشروطها |
|---|---|
| queued | الدعوات والعملية ثبتت، ومهامها محفوظة وتنتظر السعة |
| running | عامل ذو ملكية صالحة يعالج مرحلة محددة |
| completed | كل البطاقات المطلوبة صحيحة، وكل صيغ الملفات المطلوبة منشورة ومتحققة |
| partial | توجد نتائج مفيدة متحققة لكن بطاقات أو صيغة ملف أو أجزاء ما زالت فاشلة |
| failed | لا توجد نتيجة قابلة للاستخدام، أو يوجد مانع نهائي موثق |
| cancel_requested | استُلم طلب الإيقاف ولم يؤكد العامل إنهاء العمل الجاري بعد |
| cancelled | توقف العمل؛ تظهر النتائج المثبتة سابقاً وعدد العناصر التي لم تستكمل |

الاستيراد له حالات تحقق مستقلة قبل قبول إنشاء الدعوات. تعرض الواجهة تقدم البطاقات وتقدم الملفات بصورة مستقلة؛ لا تخفي PDF فاشلاً خلف عداد بطاقات مكتمل. لا تصل علامة النجاح الكامل إلى 100% قبل التحقق من المخرجات.

طلب الإلغاء يرجع قبولاً للطلب، لا ادعاء توقف فوري. يفحص العامل الإلغاء عند حدود الوحدات والمراحل، ولا ينشر مخرجات جديدة بعد تثبيته. إذا اكتمل رفع خارجي أثناء الإيقاف دون تثبيت نتيجته، يعامل كملف غير منشور للتنظيف. لا تصبح cancelled جاهزة بسبب تحديث ختامي غير مشروط.

زر إعادة المحاولة يعمل على العملية نفسها، ويعرض ما سيُعاد بالضبط: بطاقات أو PDF أو ZIP. لا يعيد خصم عدد الدعوات. تغيير البيانات أو التصميم لا يحدث بصمت داخل العملية؛ يُنشئ إجراء إصدار صريحاً أو عملية جديدة بعد بيان أثرها.

يظهر للمستخدم أن إيقاف توليد الملفات لا يلغي الدعوات المنشأة. إلغاء الدعوات أو إبطالها له صلاحيات وتدقيق وقيود تمنع الإضرار بدعوات استُخدمت بالفعل.

### مرجع 8 — الصلاحيات والروابط

| الإجراء | السياسة المطلوبة |
|---|---|
| قبول إنشاء الدعوات | invitations.create، وملكية/إتاحة الحدث، وحدود الخطة، وصلاحية الدفعات حيث تُستخدم |
| طلب RSVP | ميزة rsvp متاحة وبيانات اتصال صحيحة؛ لا يتغير pending إلى accepted بسبب تعطل الخدمة أو تعطيل الميزة |
| إنشاء/تنزيل ملف تصدير | invitations.export وميزة pdf_export؛ يعاد التحقق عند التنزيل |
| متابعة حالة العملية | منشئها أو batches.view، مع إتاحة الحدث والمؤسسة؛ الحالة المختصرة لا تمنح قراءة بيانات ضيوف إضافية |
| قائمة العمليات وتفاصيل الدعوات | batches.view مع invitations.view وإتاحة الحدث والمؤسسة؛ مسودة الاستيراد الخاصة تتطلب ملكيتها وصلاحية الإدخال |
| الإلغاء وإعادة الفاشل | batches.manage مع الصلاحيات والميزات الحالية اللازمة للعمل المطلوب |
| تعديل القالب وحذفه | صلاحيات templates الحالية وعزل المؤسسة؛ لا تتغير snapshot لعملية سابقة |
| إرسال WhatsApp | الإجراء المنفصل الحالي مع whatsapp.send وinvitations.send والميزة والتواصل الصحيح |

تُراجع صلاحيات الخادم والواجهة معاً؛ مفاتيح ui.* تنظّم العرض ولا تكون بديلاً لحراسة API. تُختبر أدوار الإنشاء دون التصدير، والقراءة فقط، والإدارة، والسوبر أدمن، والمؤسسات المرتبطة.

صلاحية إنشاء العملية الموحدة هي invitations.create؛ إنشاء الدفعات الداخلية أثر تابع للعملية المصرح بها، ولا يضيف طلباً جديداً لصلاحية batches.create على مستخدم كان يملك الإنشاء السريع. تظل batches.create مطلوبة لواجهة إنشاء الدفعات المباشرة الحالية. تُوثق هذه السياسة في adapters الانتقالية، ولا تُمنح صلاحيات جديدة للأدوار تلقائياً لتجاوز اختلاف قديم. طلب ملفات مع الإنشاء يتطلب صلاحية التصدير؛ من لا يملكها يستطيع إنشاء الدعوات دون ملفات وتظهر له النتيجة المناسبة، بدلاً من رابط غير مصرح أو رفض غامض.

تحفظ قاعدة البيانات مسار الملف، لا الرابط الموقع باعتباره مرجعاً دائماً. يطلب زر التنزيل رابطاً حديثاً عبر API بعد التحقق؛ مدة مبدئية قصيرة، خمس دقائق قابلة للضبط وفق حجم الملف والمزود. يمكن استخدام تنزيل محمي مباشر إذا كان زمن/حجم الملف لا يلائم الرابط القصير، مع مراعاة موارد الخادم. لا تُرسل JWT أو tenant header إلى أصل التخزين ولا تُسجل signed tokens في logs.

يُحفظ تدقيق قبول العملية والإلغاء والإعادة وتغيير السياسة والتنزيل حسب السياسة الحالية، دون تسجيل نص الدعوة أو الهاتف أو صفوف الاستيراد كاملة. تُراجع الصلاحيات أثناء المعالجة؛ فقدان صلاحية المنشئ أو الميزة يوقف العمل المحمي بسبب واضح، ولا يحوّل دعوة RSVP إلى دعوة مباشرة تلقائياً.

### مرجع 9 — الاستيراد والواجهة عند الأعداد الكبيرة

يرفع الملف إلى الخادم ويقرأه العامل تدريجياً، ثم تحفظ صفوفه المتحققة. يتصفح العميل الصفوف والأخطاء، ولا يرسل نسخة كاملة من 10,000 سجل عند كل تغيير أو بداية توليد.

- حدود افتراضية واضحة للحجم والصفوف والأعمدة وأطوال الحقول، متسقة بين الطرفين. يبدأ حد الملف الحالي 5MiB؛ رفعه يحتاج اختبار القراءة والذاكرة أولاً.
- تحقق من نوع الملف الفعلي وحدود فك ضغط XLSX وعدد عناصره وحجمه المفكوك قبل القراءة؛ لا يكفي حجم ZIP المضغوط.
- لا تُنفذ صيغ أو روابط خارجية. القيم المحسوبة المفقودة تعرض كخطأ واضح، والقيم النصية المصدّرة تُحمى من تفسيرها كصيغة.
- اختيار ورقة البيانات يظهر عند وجود أكثر من ورقة؛ لا تُقرأ ورقة إرشادات بالخطأ كضيوف.
- معاينة وأخطاء بصفحات، وبحث وتصنيف حسب الفئة وصحة الاتصال؛ تصدير الصفوف المخالفة لتصحيحها ورفعها مجدداً.
- الحقول الأساسية لا تُلتقط بالمطابقة الغامضة بلا مراجعة. يثبت المستخدم خريطة الأعمدة وتعرض عينة للقيم المطَبَّعة.
- إزالة الملف أو تغييره تلغي نتيجة التحقق السابقة. تغيير إعداد يؤثر على الاختيار أو RSVP يعيد التحقق قبل قبول العملية.
- المسودات الكبيرة محفوظة على الخادم؛ localStorage يقتصر على تفضيلات العرض ومعرّف المسودة غير الحساس. تهاجر المسودات الحالية بعد التحقق من صلاحية المستخدم ونجاح الحفظ، دون فقد صامت.
- استعادة العملية بالمؤسسة والحدث بعد تحديث الصفحة أو تسجيل الدخول، مع تبويب «عمليات الإنشاء» مصفح ومفلتر.
- polling محدود أثناء التشغيل، مع انتظار متزايد عند الخطأ وإيقافه عند الحالة النهائية أو إخفاء الصفحة. لا ينفذ كل صف طلباً مستقلاً للتقدم.
- رسالة قبول الطلب واضحة: «بدأت العملية، يمكنك مغادرة الصفحة ومتابعتها لاحقاً». لا يظهر نجاح الإنشاء بسبب وصول 202 وحده.

<a id="reference-10"></a>

### مرجع 10 — أهداف الأداء والقياس

الأرقام التالية أهداف قبول تُثبت على موارد staging مماثلة للإنتاج، وليست وعوداً مبنية على الخادم الحالي:

| القياس | هدف القبول الأولي |
|---|---|
| قراءة صفحة 50/100 سجل أو تقدم العملية | p95 لا يتجاوز ثانية تحت الحمل المعتمد |
| قبول عملية حتى 1,000 سجل متحقق | p95 لا يتجاوز ثانيتين، دون الرسم والرفع |
| قبول عملية 10,000 سجل متحقق | p95 لا يتجاوز خمس ثوانٍ؛ يشمل معاملة الإنشاء والحصة |
| ألف بطاقة سريعة | p95 لا يتجاوز خمس دقائق بعد حصولها على العامل، لا يشمل زمن انتظار الطابور |
| ألف بطاقة مصممة | هدف أولي 15 دقيقة لقالب قياسي محدد الأبعاد والعناصر؛ القوالب الثقيلة لها قياس مستقل |
| ذاكرة حاوية العامل | peak دون 70% من الحد المعتمد في الاختبار الطويل؛ دون OOM |
| استعادة مهمة بعد فقد العامل | بدء إعادة آمنة خلال ثلاث دقائق من توقف heartbeat |
| انقطاع Redis لمدة عشر دقائق | لا فقد لعملية مقبولة؛ يعاد نقلها بعد عودة النقل |

يفصل التقرير زمن الانتظار عن زمن التنفيذ وعن زمن التنزيل. يُقاس معدل البطاقات والصفحات والرفع، ومنه يُعرض تقدير وقت قابل للتحديث. لا تُعرض مدة دقيقة غير مبنية على قياسات.

تحدد ورقة السعة المعالج والذاكرة والقرص والمساحة المؤقتة وعرض نقل التخزين واتصالات PostgreSQL وحدود المزود، وتترك هامشاً لـAPI وقاعدة البيانات وOpenWA. يُزاد عدد العمال على خادم أكبر أو عقد منفصلة عند الحاجة؛ لا تُرفع concurrency لإخفاء بطء دون اختبار.

| تحديث الصفحة وتبديل الحساب أو الحدث والجوال وlight/dark | استعادة سليمة، دون تسرب مسودة أو فقد متابعة أو جدول غير محدود |

اختبار تحميل مستقل: 1,000 عملية صغيرة مقبولة عبر مؤسسات متعددة ضمن سقف البطاقات، وملفات 10,000 سجل، وحمل قراءة 100 مستخدم متزامن، وزيادة تدريجية لحمل قبول الطلبات. يُسجل الحمل الفعلي ومعدل القبول والانتظار و429 و5xx وزمن p95. لا يضخ الحمل مباشرة في قاعدة الإنتاج.

يضاف تشغيل طويل ثماني ساعات، واختبار إعادة تشغيل API والعامل وRedis، واختبار استعادة قاعدة البيانات والملفات والنسخ الاحتياطية. النسخ الخارجية المشفرة شرط لاستعادة فقد الخادم؛ استعادة العامل أو Redis ليست دليلاً على تحمل فقد القرص أو الخادم بالكامل.

<a id="reference-12"></a>

### مرجع 12 — المراقبة والتشغيل

لوحة تشغيل تعرض عمر أقدم مهمة، وحجم outbox غير المرسل، والدفعات ذات lease منتهية، ومعدل الإنجاز والفشل وإعادة المحاولات، وذاكرة العامل، ومساحة العمل والتخزين، وزمن قراءة API. المؤشرات لا تستخدم أرقام الهواتف أو الأسماء كـlabels، ولا تنشئ سلسلة مراقبة لكل دعوة.

تنبيهات أولية: عملية مقبولة بلا نقل أكثر من دقيقتين، heartbeat منقطع، انتظار أقدم من ميزانية الطابور المعتمدة، ذاكرة فوق 80%، مساحة عمل دون 20%، أو ارتفاع فشل التصدير. هذه مؤشرات تشغيل قابلة للضبط بحسب القياس، وليست ادعاء زمن إنهاء لكل عملية.

دليل التشغيل يحدد كيفية إيقاف قبول أعمال جديدة، والتحقق من leases، واستعادة حدث outbox، وإعادة مرحلة فاشلة، وتنظيف ملف غير منشور، واسترجاع backup. لا يعالج التعطل بتغيير الحالات إلى ready أو حذف الدعوات لتجاوز الحصة.

<a id="reference-14"></a>

### مرجع 14 — التوافق والنشر والرجوع

1. تؤخذ نسخة احتياطية مشفرة وتُختبر الاستعادة، وتُحفظ صور API والعامل والواجهة للرجوع.
2. تنشر ترحيلات إضافية متوافقة، دون حذف أعمدة أو حالات أو سجل قديم. لا تُعاد تسمية enum المنشورة بطريقة تكسر العميل السابق.
3. تُضاف واجهات عمليات جديدة بعقد موثق. لا يتحول رد الواجهة السريعة القديمة من success/URLs إلى 202 بصمت.
4. يحصر ويُرحّل كل مستهلك للإنشاء، لا EventInvitationsTab وحده. تبقى الواجهات القديمة تحت حدودها الانتقالية إلى أن يثبت ترحيل المستهلكين؛ لا تصبح منفذاً بديلاً يتجاوز الصلاحيات أو سقوف الحمل.
5. يبدأ تفعيل القبول الجديد في staging، ثم مؤسسة اختبار محددة، ثم توسع تدريجي مقترح 10% و50% و100% بعد اجتياز القياس. التنفيذ واحد للطلب؛ لا يشغل المحركان نفس الدعوات كاختبار مقارنة.
6. لا تعاد الدفعة الإنتاجية القديمة المعلقة تلقائياً بمجرد نشر الإصلاح. تُراجع عناصرها وملفاتها وسبب انتظارها وتُستعاد ضمن الإجراء المدقق، دون إنشاء دعوتين للسجل نفسه.
7. عند تدهور النتائج يوقف flag قبول عمليات جديدة أولاً. تظل قراءة العمليات وتنزيل النتائج والعامل المتوافق متاحة لاستكمال أو إيقاف المقبول بالفعل.
8. لا يُرجع العامل إلى نسخة لا تفهم بيانات العمليات الجديدة بينما توجد أعمال مقبولة. يُنشر إصلاح متوافق أو يستكمل/يوقف العمل قبل الرجوع الثنائي؛ لا تُحذف جداول جديدة لإجبار rollback.
9. تقارن أعداد الدعوات والعمليات والعناصر والملفات واستخدام الحصص قبل النشر وبعده، وتُفحص عينات طباعة وتنزيل وصلاحيات.
10. تنتهي المرحلة الانتقالية بعد توثيق جميع المستهلكين والنتائج، وإغلاق المسار المتزامن القديم بطريقة معلنة ومدروسة.

### مرجع 15 — متى نعلن «جاهزاً للإنتاج»؟

لا يُعلن ذلك بمجرد نجاح البناء أو اختبارات الوحدة. يلزم سجل تحقق يثبت:

- اكتمال كل حالات العيوب المثبتة في المراجعة وعقد واضح للمدخلات والحالات.
- نجاح اختبارات قاعدة البيانات وRLS والصلاحيات والواجهة والملفات، بما فيها العربية وQR.
- نجاح 10,000 سجل، وآلاف العمليات المنتظرة ضمن سقف البطاقات، وحمل القراءة والتزامن، مع موارد وحدود موثقة.
- عدم فقد أو تكرار دعوات/حصص عند انقطاع API أو العامل أو Redis، وعدم إعلان جاهزية ناقصة.
- إلغاء فعلي واستعادة ومتابعة بعد تحديث الصفحة، وإعادة الفاشل دون إنشاء جديد.
- مراقبة وتنبيهات ودليل تشغيل ونسخ خارجية واستعادة مثبتة وخطة رجوع متوافقة.
- تحقق الإنتاج التدريجي على ملفات وعمليات مصرح بها، دون إرسال رسائل للعملاء ضمن اختبارات التوليد.

الأولوية التنفيذية الأولى هي P0، ثم P1 وP2. هذه المراحل تجعل صحة العملية واستمرارها قابلة للاعتماد؛ تليها P3 وP4 لاستيعاب الحجم وتحسين الاستخدام، ثم لا يُفتح الحد الإنتاجي الأكبر إلا بعد P5 وP6.
