# تقييم جاهزية OpenWA

تاريخ المراجعة: 12 أكتوبر 2026. النطاق: ملفات `OpenWA` والكود المحلي لمنصة الدعوات. هذه مراجعة ساكنة وإعدادات تشغيل؛ لم تُشغّل جلسة WhatsApp ولم تُرسل رسائل فعلية.

## القرار

**ليست جاهزة للاعتماد الإنتاجي أو لإرسال دعوات العملاء حالياً.** يوجد تنفيذ معتبر يمكن تطويره وتجربته في بيئة معزولة بعد إصلاح الاعتماديات، لكن وجود الملفات وواجهات API لا يثبت نجاح التشغيل أو التسليم.

هذه نسخة NestJS تعتمد `whatsapp-web.js` ومتصفح Chromium. ليست تكاملاً منفذاً مع WhatsApp Cloud API. لا يصح افتراض ضمان استمرارية الجلسة أو التسليم من أسماء الميزات في README.

## ما هو موجود

- إدارة جلسات وربط QR، ومحاولة استعادة الجلسات ذات بيانات اتصال محفوظة عند بدء الخدمة: `src/modules/session/session.service.ts`.
- إرسال نصوص ووسائط ومستندات، وإرسال جماعي مع تقدم ونتائج لكل رسالة: `src/modules/message`.
- مفاتيح API مخزنة كـhash، وأدوار وقيود IP والجلسات، وحارس HTTP عام وحدود طلبات: `src/modules/auth`.
- Webhooks للأحداث، وتوقيع HMAC عند توفير secret، ومحاولات إعادة إرسال. توجد BullMQ queue للـWebhooks عند تفعيلها.
- لوحة React، ومهاجرات قاعدة البيانات، وDocker وإعداد staging.

## النتائج التي تمنع الاعتماد

| الأولوية | النتيجة المثبتة في الكود | الأثر والمعالجة |
|---|---|---|
| P0 | `events.gateway.ts` يتحقق من المفتاح دون تمرير IP أو sessionId، ثم يسمح بالاشتراك في sessionId المرسل دون فحص allowedSessions | قيود المفتاح لا تعزل أحداث WebSocket كما تعزل بعض طلبات HTTP. يلزم التحقق قبل الاشتراك وعند الإبطال، مع اختبارات بين جلستين ومفتاح مقيد. |
| P0 | `infra.controller.ts` لا يضع RequireRole على تعديل config وrestart وimport-data وstorage/import؛ الحارس العام يفرض وجود مفتاح، لكنه لا يفرض ADMIN دون decorator | يستطيع مفتاح أدنى دور الوصول إلى إجراءات بنية حساسة بحسب الكود الحالي. يلزم قصرها على ADMIN ومراجعة المسارات الإدارية كافة. |
| P0 | Dockerfile ينشئ مستخدم openwa لكنه لا يستخدم USER؛ Compose يركب docker.sock | الخدمة تعمل افتراضياً كـroot مع وصول إلى Docker daemon. تركيب socket بـro لا يجعل عمليات Docker API للقراءة فقط. يلزم إزالة socket من خدمة الإرسال وفصل الإدارة إن لزمت، وتشغيل المستخدم المحدود. |
| P1 | bulk-message.service.ts يبدأ processBatch داخل العملية، ويتتبع الإلغاء بذاكرة Map، ويحفظ التقدم كل عشر رسائل تقريباً | لا توجد آلية استئناف تلقائي للدفعات في هذا المسار بعد restart. توجد نافذة بين الإرسال وحفظ النتيجة قد تؤدي إلى تكرار عند إعادة المحاولة. يلزم Queue دائمة لكل رسالة، وoutbox ومفتاح محاولة ثابت، ومعالجة الحالة غير المحسومة. تفعيل Queue الحالية للـWebhooks لا يحل ذلك. |
| P1 | API guard يقرأ x-forwarded-for مباشرة؛ فحص allowedIps يُتجاوز عندما لا يمرر المستدعي clientIp | لا يمكن الاعتماد على قائمة IP دون ضبط proxy موثوق والتحقق المتسق. يلزم اعتماد IP المستخرج وفق حدود الثقة، وتطبيق القيود في HTTP وWebSocket. |
| P1 | webhook.service.ts يستخدم fetch لعنوان يحدده المستخدم؛ التحقق في DTO هو IsUrl. الوسائط تُحمّل بـMessageMedia.fromUrl | لا توجد في المسارات المراجعة حماية واضحة من الوصول لعناوين الشبكة الداخلية أو التحويلات إليها. يلزم تقييد الوجهات والتحقق من DNS وredirects وحدود تنزيل الوسائط. |
| P1 | main.ts يحمل .env مع override:true رغم تعليق يقول إن process env أعلى أولوية | قد تُستبدل إعدادات التشغيل الممررة من البيئة. يلزم توحيد أولوية الإعدادات واختبارها قبل النشر. |
| P1 | staging يشغل Caddy مستقلاً على 80 و443، والخادم الحالي يشغّل qentry-prod-caddy على المنافذ نفسها | الإعداد لا يصلح للتشغيل كما هو بجانب الموقع الحالي. يلزم دمجه خلف proxy الحالي أو عزله على خادم آخر. |
| P1 | مسار platform `app/routes/digital_invitations.py` يضع WhatsApp ضمن unsupported_channels ويرجع 501 | الخدمة غير مربوطة بإرسال الدعوات الحالي. يلزم adapter خلفي وصلاحيات وQueue وسجل تسليم، ولا يوضع مفتاح OpenWA في المتصفح. |

## التحقق المنفذ وحدوده

- لا توجد حاوية OpenWA ضمن الحاويات العاملة وقت المراجعة.
- `docker compose ... --profile postgres config --quiet` يفشل بالإعداد الحالي لأن OPENWA_DOMAIN غير معرّف. نجح التحقق البنيوي عند تمرير نطاق وهمي وعنوان loopback مؤقتين؛ لم يبدأ أي container.
- `npm test -- --runInBand` فشل بـ`jest: Permission denied`. محاولة استدعاء Jest عبر Node أكدت غياب ملف `node_modules/jest/bin/jest.js`.
- محاولة البناء عبر Nest CLI فشلت بسبب غياب ملف `glob/dist/commonjs/index.min.js`. مجلد node_modules الحالي لا يمثل تثبيتاً سليماً يمكن اعتماد نتائجه.
- لم تُثبت سلامة build الواجهة أو نجاح migrations على قاعدة جديدة أو استعادة backup أو اتصال WhatsApp أو إرسال PDF فعلي. الاختبارات المكتوبة ليست نتيجة اختبارات ناجحة.

## آلية ربط مناسبة لمنصة الدعوات

1. يحفظ الخادم طلب إرسال بعد التحقق من مساحة العمل والصلاحيات وصلاحية الدعوة ورقم المستلم. يرسل رابط RSVP لمن ينتظر الرد، والتذكرة المؤهلة لمن يحق له الدخول.
2. ينشئ سجل إرسال وjob دائمة بمعرف ثابت؛ العامل الخلفي يختار جلسة مساحة العمل المصرح بها ويستدعي OpenWA بمفتاح محدود من الخادم.
3. تتوقف jobs عند غياب جلسة READY، وتظهر حالة «بانتظار اتصال WhatsApp» للمشغل. لا تُسجل الدعوة كمُرسلة لمجرد إدراجها في Queue.
4. تُفصل حالات queued / sending / sent / delivered / read / failed / unknown. قبول استدعاء الإرسال ليس إثبات وصول الرسالة أو موافقة الضيف على الحضور.
5. يتحقق مستقبِل Webhook من التوقيع ومعرف الحدث ويمنع تكرار تطبيقه؛ تُعاد محاولات الأخطاء المؤقتة فقط، وتُراجع unknown قبل إعادة الإرسال.
6. تكون إعادة الإرسال إجراءً واضحاً بعد فحص الحالة، ويوقف إلغاء الدعوة أي job لم تبدأ. الرسالة التي وصلت سابقاً لا يمكن افتراض سحبها؛ يظل قرار دخول التذكرة عند الخادم.

## ترتيب الوصول إلى الجاهزية

إصلاح P0 أولاً، ثم تثبيت نظيف من lockfile وبناء واختبارات في بيئة معزولة، ثم اختبار migrations والنسخ والاستعادة، ثم إرسال تجريبي مصرح لرقم اختبار مع حالات انقطاع الجلسة وrestart وفقد الرد وWebhooks المكررة. بعد ذلك يُنفذ الربط الخلفي وتُختبر حدود مساحة العمل والدفعات. لا تُرفع دفعة عملاء قبل إثبات هذه الحالات.

هذه المراجعة لم تغيّر سلوك الخدمة ولم تنشرها. لا تتضمن الوثيقة أسرار البيئة أو بيانات جلسات WhatsApp.
