# خطة تشغيل OpenWA وربط إرسال الدعوات

**الحالة: خطة تنفيذ جاهزة؛ الخدمة لم تُعتمد أو تُشغّل بهذه الخطة بعد.** تاريخ الإعداد: 12 أكتوبر 2026. المرجع: [تقييم الجاهزية](OPENWA_READINESS_AR.md).

## النتيجة المطلوبة

يختار المشغل دعوات مؤهلة، يعاين الرسالة والمستلمين، ثم يطلب الإرسال. تتولى الخدمة الخلفية الإرسال وتتبع النتائج. عند انقطاع WhatsApp تظهر حالة انتظار واضحة، وعند ضياع رد الإرسال لا تُرسل الرسالة مرة أخرى تلقائياً دون حسم المحاولة السابقة.

قرار التنفيذ المقترح: PostgreSQL لسجلات الإرسال، وQueue منصة الدعوات لإدارة jobs، وOpenWA بوابة إرسال جلسات. لا نعتمد bulk endpoint الحالي للدفعات الإنتاجية قبل إصلاح استدامته. تُدار جلسة واحدة في عامل OpenWA واحد؛ التوسع لاحقاً بتوزيع الجلسات، لا بتشغيل متصفحين على ملفات الجلسة نفسها.

## مراحل التنفيذ ومعايير الانتقال

| المرحلة | العمل المحدد | شرط الانتهاء |
|---|---|---|
| 1 — قابلية البناء | تثبيت نظيف من lockfiles في بيئة Node 22 مع أدوات بناء SQLite؛ بناء API واللوحة؛ تشغيل unit وe2e على قاعدة اختبار | بناء ناجح ونتائج اختبارات محفوظة، دون استخدام بيانات الجلسات الفعلية |
| 2 — الحماية | فرض ADMIN على إدارة البنية والإضافات والإعدادات؛ عزل HTTP وWebSocket بحسب allowedSessions؛ التحقق من IP عبر proxy موثوق؛ معالجة الإبطال؛ حماية وجهات webhooks والوسائط وأحجام التنزيل | مفتاح مساحة A لا يقرأ أو يرسل أو يشترك في جلسة B؛ مفتاح operator لا يعدل البنية؛ الوجهات الداخلية غير المصرح بها مرفوضة |
| 3 — التشغيل | إزالة docker.sock من خدمة الإرسال؛ USER محدود وصلاحيات volume صحيحة؛ أولوية process env؛ إعداد نشر عبر شبكة داخلية وproxy الحالي؛ migrations وbackup | تشغيل واستعادة قاعدة جديدة ونسخة backup بنجاح، دون تعارض 80/443 أو كشف API عام |
| 4 — استدامة الإرسال | سجل محاولة ثابت وoutbox ومعالجة idempotency في بوابة الإرسال؛ فصل حالة unknown؛ قفل التنفيذ لكل محاولة؛ استئناف jobs؛ backoff للأخطاء المؤقتة | restart أو تكرار job لا يبدأ محاولة إرسال ثانية لنفس المعرف؛ فقد الرد يؤدي إلى unknown ومراجعة، لا retry أعمى |
| 5 — الربط | adapter خلفي، إعداد جلسة ومفتاح لكل مساحة، endpoint طلب إرسال، webhooks موثقة ومتحقق منها، صلاحيات وfeature flag | مسار WhatsApp يدرج طلباً صحيحاً بدلاً من 501؛ الاستدعاء لا يعلن التسليم قبل الدليل |
| 6 — الواجهة | معاينة وإرسال، سجل حالات، انتظار الاتصال، إعادة إرسال محددة، إعداد جلسة للمخولين | المستخدم يعرف لمن أُرسلت الرسالة وما الذي ينتظر أو فشل وما الإجراء التالي |
| 7 — الاعتماد | اختبار فعلي مصرح به لرقم اختبار، ثم دفعة صغيرة محددة ومراقبة، ثم توسيع تدريجي | اجتياز مصفوفة القبول أدناه وتوفر إجراء تعطيل واسترجاع مجرب |

لا تحدد مدة زمنية قبل تثبيت الاعتماديات وقياس تكلفة تشغيل المتصفح وحجم الدفعات. أرقام throughput أو retry القصوى تُضبط من تجربة التشغيل، وليست ضماناً لسعة WhatsApp.

## عقود مقترحة تحتاج تنفيذاً

جميع العقود في هذا القسم **مقترحة وليست endpoints موجودة**.

`POST /api/v1/events/{event_id}/whatsapp-deliveries` يستقبل `invitation_ids` و`purpose` و`client_request_id`. يتحقق الخادم من الصلاحية والنطاق وأهلية كل دعوة، ويحفظ الطلب وoutbox داخل معاملة واحدة، ثم يعيد 202 مع `request_id` وأعداد queued/skipped/rejected. تكرار client_request_id مع payload نفسه يعيد الطلب السابق؛ اختلاف payload يعيد 409.

`GET /api/v1/events/{event_id}/whatsapp-deliveries` يعرض سجلاً مقيداً بالحفل مع pagination وفلترة الحالات. `POST /api/v1/whatsapp-deliveries/{delivery_id}/retry` يسمح بإعادة محاولة failed القابلة للإعادة؛ لا يعيد unknown أو delivered تلقائياً. إعادة إرسال رسالة وصلت هي إجراء جديد مقصود ومدقق، له معرف جديد.

`POST /api/v1/integrations/openwa/webhook` يستقبل الأحداث بعد التحقق من HMAC على bytes الأصلية. يربط sessionId وwaMessageId بالسجلات المعروفة، ويتجاهل التكرار بمعرف الحدث. عنوان عام للـwebhook لا يتطلب إتاحة API OpenWA العامة.

## نموذج السجلات المقترح

| السجل | الحقول الأساسية | الضمان المطلوب |
|---|---|---|
| whatsapp_connections | tenant_id, session_id, secret_reference, status, last_seen_at | المفاتيح في مخزن أسرار خلفي؛ mapping موثوق لكل مساحة؛ إسناد اتصال مشترك صريح إذا اعتمد |
| delivery_requests | id, tenant_id, event_id, client_request_id, payload_hash, created_by | unique للطلب داخل مساحة العمل |
| whatsapp_deliveries | id, request_id, invitation_id, purpose, recipient, state, attempt_id, wa_message_id, error_code, next_retry_at | معرف ثابت للمحاولة؛ منع job مكررة؛ قيود unique مناسبة للسياق |
| delivery_outbox | id, delivery_id, published_at, attempts | حفظ نية الإرسال مع الطلب atomically؛ نشر قابل للإعادة |
| webhook_receipts | connection_id, event_id, received_at, payload_hash | unique لمنع تطبيق الحدث مرتين؛ الاحتفاظ بالحد الأدنى اللازم |

يلزم migration إضافية داخل OpenWA لحفظ attempt_id ونتيجة المحاولة والتحكم في إعادة الطلب. Outbox وحدها لا تمنع تكرار إرسال خارجي وقع قبل فقد الرد. إذا وقع انقطاع بعد البدء ولم يوجد دليل حاسم، تنتقل المحاولة إلى unknown؛ لا ندعي exactly-once من WhatsApp.

## متى يُتاح الإرسال؟

| حالة الدعوة أو الاتصال | السلوك |
|---|---|
| RSVP مفعلة والضيف ينتظر الرد | إرسال رابط طلب تأكيد الحضور؛ لا إرسال رمز دخول مؤهل قبل الموافقة |
| الضيف وافق والدعوة صالحة | إرسال رابط التذكرة أو مستند الدعوة الفردية بحسب الإعداد |
| RSVP غير مطلوبة والدعوة صالحة | إرسال التذكرة مباشرة |
| الدعوة ملغاة أو منتهية أو الضيف اعتذر | رفض إرسال تذكرة دخول وشرح السبب |
| لا يوجد رقم صالح | استبعاد مع سبب قابل للتصحيح؛ توحيد الرقم بصيغة دولية دون تخمين البلد |
| رقم صالح وجلسة غير READY | حفظ job في waiting_connection، دون اعتبارها sent |
| إرسال سابق unknown | إيقاف retry التلقائي وإظهار طلب مراجعة |
| إلغاء الدعوة وهي queued | إلغاء job؛ يعيد العامل فحص الأهلية مباشرة قبل التنفيذ |
| إلغاء الدعوة بعد sent | يبقى سجل الإرسال؛ تبطل أهلية الدخول عند الخادم؛ لا يدّعي النظام سحب رسالة وصلت |

لا يرسل PDF جماعياً يتضمن تذاكر الضيوف الآخرين. تحميل المستند يتم خلفياً، مع تقييد مصدره وTTL وحجمه؛ لا يظهر مفتاح OpenWA أو رابط حزمة جماعية في رسالة الضيف.

## الحالات والواجهة

الحالات: queued → sending → sent → delivered → read. الحالات الإضافية: waiting_connection / failed / unknown / cancelled. تُحدّث delivered وread فقط بأحداث موثوقة يدعمها المحرك فعلياً؛ غياب read لا يعني الفشل. لا يُسمح لحدث متأخر بخفض delivered إلى sent.

في شاشة الدعوات: زر «إرسال عبر WhatsApp» للمخولين عند تفعيل الخدمة، ثم معاينة النص وعدد المؤهلين وأسباب الاستبعاد. بعد الطلب تظهر حالة مستقلة لكل ضيف. تُعرض إعدادات الربط وQR للمخولين بالإدارة فقط، مع «متصل»، «بانتظار الربط»، «منقطع»، ووقت آخر تحقق. لا تكون الموافقة على RSVP ناتجة عن قراءة الرسالة.

## مصفوفة القبول

- منع الإرسال والاشتراك بين مساحتي عمل، ورفض إدارة البنية بمفتاح operator.
- إرسال نص ورابط RSVP وPDF فردي لرقم اختبار مصرح، وربط النتيجة بالضيف الصحيح.
- تكرار طلب المستخدم وتكرار job وwebhook لا ينشئ إرسالاً جديداً أو يضاعف النتائج.
- توقف العامل قبل الاستدعاء وبعده، وضياع الرد، وانقطاع الجلسة: حالات صحيحة واستئناف دون retry أعمى.
- إلغاء دعوة أو اتصال وإزالة صلاحية المشغل قبل تنفيذ job يمنع إرسالاً جديداً.
- توقيع webhook غير صحيح أو حدث مكرر أو sessionId مجهولة لا يغير سجل التسليم.
- تنزيل وسائط بحجم زائد أو redirect غير مصرح أو عنوان داخلي غير مسموح يُرفض.
- migrations على قاعدة فارغة واستعادة backup تشمل قاعدة OpenWA وبيانات الجلسات ومراجع الأسرار؛ اختبار صحة الصلاحيات بعد الاستعادة.
- فشل WhatsApp لا يؤثر على تسجيل الدخول والمسح وإرسال البريد في منصة الدعوات.

## النشر والاسترجاع

تُبنى صور بإصدارات ثابتة وتُنشر أولاً في staging مع قواعد وvolumes مستقلة. على الخادم الحالي يستخدم proxy الموقع الموجود؛ لا يُشغّل Caddy ثانٍ على 80/443. يُنسخ احتياطياً قبل migrations، ويُفحص توافق الإصدار السابق قبل اعتماد الرجوع إليه.

التفعيل الإنتاجي يبدأ مع feature flag معطلة، ثم اتصال اختبار ومساحة محددة. عند الفشل: تعطيل إنشاء طلبات جديدة، إيقاف إرسال jobs الجديدة مع حفظها، تصنيف sending غير المحسومة unknown، ثم استرجاع الإصدار المناسب. لا تعاد jobs غير المحسومة تلقائياً ولا تحذف الأدلة.

متطلبات خطوة الربط الفعلي: تحديد مساحة الاختبار، رقم WhatsApp الذي سيُربط بواسطة صاحبه، ورقم مستلم اختبار مع إذن إرسال محدد. بقية الإصلاحات والبناء والاختبارات المعزولة لا تعتمد على هذه البيانات. وصول المشروع إلى مرحلة «شغال» يُثبت بنتائج الاختبارات والتشغيل، لا بإتمام كتابة الخطة.
